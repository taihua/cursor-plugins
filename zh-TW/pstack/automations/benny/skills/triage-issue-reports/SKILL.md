# Triage issue reports（分類問題回報）

為一則 Slack 回報分類，並在它的來源討論串中貼出一則有用的判定。只為明確的新 bug 建立追蹤系統議題。不要在這裡重現或修正它。

載入自動化提供的外部 Benny 設定。如果設定缺少、格式錯誤或不完整，就停下，不要貼文，也不要寫入追蹤系統。

## 硬性安全規則

- 來源頻道和根討論串的座標是不可變的。
- 永遠不要在來源頻道中發根訊息。
- 永遠不要貼文到其他頻道、廣播回覆、傳私訊，或另開一個替代的討論串。
- 在任何追蹤系統寫入之前，以及在貼出判定之前的那一刻，對來源父訊息做預檢。
- 如果父訊息缺少、已刪除、無法存取或不確定，就停下，不做任何寫入。
- 貼一則實質的判定。不要敘述進度。
- 協調者是唯一的 Slack 貼文者。
- 被委派的 worker 只回傳發現。它們必須是唯讀的，不能拿到 Slack 憑證或寫入動作。
- 每個子代理的提示詞都必須禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage` 以及所有其他 Slack 寫入。
- 如果 worker 的隔離無法強制這些限制，就在協調者中做這份工作。
- 永遠不要建立一個無法連回來源討論串的議題。
- 寧可不開工單，也不要開一張猜測的或重複的工單。
- 對來源座標套用 pstack 的 `principle-separate-before-serializing-shared-state`。
- 對最終判定套用 pstack 的 `principle-minimize-reader-load` 和 `unslop` 技能。

## 1. 凍結來源座標

在列工作清單或委派之前：

1. 從觸發中讀取 `source_channel_id`。
2. 要求它等於設定的來源頻道。
3. 如果有 `trigger.thread_ts`，就把 `SOURCE_THREAD_TS` 設為它。否則使用 `trigger.ts`。
4. 要求 `SOURCE_THREAD_TS` 不為空。
5. 把 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 儲存為不可變的值。
6. 讀取討論串，確認它的根訊息恰好有那些座標。
7. 取得一個穩定的來源永久連結。

之後每一次對來源的讀取和貼文都必須使用那些儲存的值。永遠不要用某則回覆的時間戳記或維運討論串的時間戳記取代它們。

## 2. 讀完整份回報

在決定之前，讀根訊息和目前的回覆。

擷取：

- 回報者的措辭
- 有的話：產品版本、app 建置版本、環境和平台
- 預期行為
- 觀察到的行為
- 頻率和觸發條件
- 錯誤文字或堆疊特徵
- 既有的議題、commit 或 PR 連結
- 任何明確表示已經有人在修的說法

檢查每個相關的附件。

- 以足夠的解析度讀截圖。
- 審查影片中區分正確與壞掉行為的那個狀態轉換。
- 讀 log、trace 和當機文字，找具體的特徵。
- 如果媒體需要專門審查，就用一個唯讀的媒體 worker，問一個範圍很窄的問題。worker 只回傳發現。
- 如果某個附件無法讀取，在判定中說明。不要捏造它顯示了什麼。

在要求回報者提供更多資訊之前，先用討論串中已有的證據。

## 3. 導向之前先追溯原因

在選擇負責人或目的地之前，做一次有範圍限制的原始碼與歷史檢查。用 pstack 的 `how` 技能追蹤從回報的動作到觀察到的結果的路徑。當回報看起來像退步或碰到防禦性程式碼時，用 `why`。

1. 找出從回報的動作到觀察到的結果最可能的程式路徑。
2. 檢查可見的症狀屬於那條程式路徑，還是它下面的某個相依。
3. 當回報看起來像退步時，檢查最近的改動。
4. 檢查是否已經有合併的 commit 或開啟中的 PR 處理了同樣的症狀。
5. 區分確認的事實和假設。

這次檢查不需要完整的根本原因。但它必須強到足以避免把一個可見的症狀導向錯誤的負責人。

如果無法讀取 repository，不要猜測程式碼負責人。繼續以保守的分類進行，並說明無法追溯原因。

## 4. 分類

選一個類別。

### Bug

某件事違反了預期行為。例如錯誤的輸出、壞掉的狀態、錯誤、當機、卡住、默默沒有動作，或退步。

### 效能（Performance）

回報描述的是可量測的緩慢、過多的記憶體、耗電、卡頓或其他資源問題。把它當作 bug 處理，但保留量測數據和效能分析。

### 功能請求（Feature request）

目前的行為看起來是刻意的，而回報者想要不同的行為或功能。

### 問題或回饋（Question or feedback）

回報在問某個東西怎麼運作、表達一個沒有具體缺陷的偏好，或給出一般的回饋。

### 轉介（Reroute）

原因追溯顯示另一個設定的目的地擁有這個問題。

當 bug 和功能請求之間的界線不清楚時，不要開單。唯一的那則判定可以問一個聚焦的問題，並使用 `other` 標記。

## 5. 套用設定的導向

從 `routing.map_path` 讀取選用的導向地圖。

- 依確認的產品區域、程式路徑或錯誤特徵比對。
- 當原因追溯指向別處時，光靠可見的症狀不夠。
- 如果沒有符合的路線，就說負責人不明確。不要猜。
- 不要跨頻道貼文。在來源討論串中告訴回報者要把問題帶到哪裡。

通知負責人預設關閉。只有在以下全部成立時才允許通知：

1. 導向地圖明確指名了負責人。
2. 設定允許那種通知類型。
3. 這個項目是需要負責人意見的功能請求，或者最近的歷史有強烈證據指出一個很可能造成退步的作者。
4. 負責人不是一個廣泛的值班群組。

其他情況一律不通知。

## 6. 使用議題追蹤系統轉接器

追蹤系統是一個轉接器，而不是必須的廠商。Linear 轉接器是一個有效的例子。GitHub Issues 轉接器或其他追蹤系統也可以實作同樣的規範。

設定的轉接器必須提供：

- 依文字、狀態、標籤、來源網址和日期範圍搜尋議題
- 讀取一個議題及其連結
- 用標題、內文、狀態、標籤和來源網址建立議題
- 更新既有議題，而不取代無關的欄位
- 新增來源連結和重複發生的說明
- 如果 Slack 交接失敗，取消、關閉或刪除這次執行建立的議題

如果缺少某個必要的操作，該次寫入就安全地失敗。

在執行期解析設定的團隊、專案、狀態和標籤。除非設定明確要求，否則不要捏造 ID、建立標籤、指派負責人或設定優先順序。

## 7. 去重

一定要檢查這個來源永久連結是否已經連結到某個追蹤系統議題，或之前的分類回覆。如果是，就不要貼文或建立重複的項目。

對於 bug 和效能回報，用以下資訊搜尋追蹤系統：

- 確切的錯誤或當機特徵
- 產品區域
- 觸發條件
- 症狀
- 版本或日期範圍
- 疑似造成退步的 commit
- 來源永久連結

選一個結果：

- 有把握的重複：相同的特徵，或相同的區域、觸發條件和症狀，或確認的共同原因。
- 可能相關：共同原因說得通，但沒有被證明。
- 微弱的相似：相似之處很表面。
- 沒有符合。

對於有把握的重複，用來源永久連結和一句簡短的重複發生說明更新既有的議題。除非設定要求，否則不要重新開啟、重新標籤或重新指派它。

對於可能的符合，在判定中以「不確定」連結它，不建立任何東西。

一個關閉很久的議題是退步的線索，而不會自動成為一個仍存在的重複項目。

## 8. 決定是否建立

只有在以下全部成立時才建立：

1. 分類是 bug 或效能。
2. 行為明顯壞掉了。
3. 問題仍然存在，或不知道已被修好。
4. 去重沒有找到有把握或說得通的、仍存在的符合項目。
5. 來源父訊息和永久連結通過了預檢。
6. 追蹤系統的目標欄位已解析。
7. 如果判定貼文失敗，轉接器能進行補償。

永遠不要為功能請求、問題、回饋項目、轉介、可能的重複、有把握的重複，或已經修好的問題建立議題。

新的議題必須自成一體：

- 簡單的標題，寫明區域和症狀
- 回報者的原話
- 預期和觀察到的行為
- 版本和環境，或 `unknown`
- 觸發條件和頻率
- 來源討論串的永久連結
- 簡短的原因追溯發現，把假設標示為假設
- 有支援時，內嵌截圖或具代表性的影片畫格
- 其餘成品的連結
- 設定的收件狀態和標籤

不要把猜測的根本原因放進標題。

## 9. 貼出一則判定

做一次全新的來源父訊息預檢。然後以 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 恰好貼出一則回覆。

永遠不要在沒有非空 `thread_ts` 的情況下呼叫來源頻道的貼文動作。

回覆保持簡短：

- 以結果開頭。
- 有的話，連結既有或新建的追蹤系統議題。
- 需要時，提到轉介或一個缺少的事實。
- 最多包含一個被允許的負責人通知。
- 以恰好一行標記結束。

標記規範：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

只使用設定的標記字串。重現自動化只有在標記來自這個來源討論串中設定的分類身分時才相信它。

貼文後，讀同一個來源討論串，確認判定出現在 `SOURCE_THREAD_TS` 底下。如果沒有，永遠不要改在根層級重試。

如果這次執行建立了追蹤系統議題，而判定沒有成功送達，就使用轉接器的補償動作。確認議題已被取消、關閉或刪除。如果無法確認補償完成，只在自動化執行的輸出中回報這個失敗。

## 10. 觀察一個後續時間窗

在設定的後續時間窗內觀察來源討論串，然後停止。

- 只回答直接問分類身分的問題。
- 在安全時，對追蹤系統議題套用具體的更正。
- 在同一次執行中不要發出第二個標記。
- 不要介入人與人之間的協調和閒聊。
- 如果有人要求自動化停止，就提早停止。

不要延長時間窗超過一次。新的回報應該開始一次新的執行。
