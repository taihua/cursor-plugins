# Verify an existing fix（驗證既有的修正）

當一個開啟中的 PR 或已合併的 commit 合理地修正了這份回報時，使用這個模式。

既有的成品擁有這個修正。驗證它。不要修改它、撰寫一個競爭的補丁，或開另一個 PR。

## 判定成品是否合格

要求一個具體的成品：

- 一個開啟中、有處理該症狀的程式碼改動的 PR
- 一個已合併的 PR
- 一個程式碼和意圖都符合的已合併 commit

討論串中的主張、追蹤系統狀態、分支名稱，或沒有 PR 或 commit 的原因假設，都不夠。

當有好幾個成品時，選擇從來源討論串或追蹤系統連結的那一個。否則選擇最接近受影響程式碼的那一個，並說明原因。

## 保護工作目錄

當 repository 支援時，使用隔離的 worktree 或另一個乾淨的 checkout。不要覆寫使用者的修改。

記錄：

- 基準版本
- 打過補丁的版本
- PR 或 commit 網址
- 兩次執行共用的建置和環境輸入

使用一般的 `github.com` PR 連結。

## 量測基準

對於開啟中的 PR，用它的基底分支作為基準。

對於已合併的修正，當修正之前的那個版本能建置、而且代表舊的行為時，就用它作為基準。

透過設定的 control 轉接器：

1. 啟動基準 app。
2. 確認 app 和環境是正確的。
3. 透過真實的 UI 動作跑回報中的路徑。
4. 觀察具辨識性的症狀。
5. 重設並重複一次。
6. 擷取基準的錄影、截圖和狀態檢查。

如果症狀沒有在基準上出現兩次，就沒有基準。不要宣稱修正有效。

## 量測打過補丁的版本

用同樣的環境和資料，建置並執行 PR 或修正 commit。

1. 跑同一條 UI 路徑。
2. 重複兩次。
3. 確認壞掉的狀態消失了。
4. 確認預期的狀態出現了。
5. 擷取修正後的錄影、截圖和同樣的狀態檢查。

不要停在編譯或測試。修正後的結果必須來自一個執行中、打過補丁的 app。

## 結果

### 已確認（Confirmed）

基準重現了兩次，而打過補丁的版本兩次都解決了它。

- 把維運狀態標為已驗證。
- 連結成品。
- 在來源預檢之後，貼一則簡潔的來源討論串回覆。
- 包含前後對照的結果。
- 不開 PR。

### 修正不足（Insufficient fix）

症狀在基準和打過補丁的版本上都出現。

- 把維運狀態標為已重現但未修正。
- 連結成品，並說明它沒有解決症狀。
- 如果這次執行還沒用過，就貼一般的「確認重現」來源更新。
- 不開競爭的 PR。

### 無法判定（Inconclusive）

基準沒有重現、打過補丁的 app 無法執行，或證據沒有顯示具辨識性的狀態。

- 不要宣稱成功。
- 說明哪一半無法量測。
- 把結果保留在維運討論串或執行輸出中。
- 除非有直接的問題需要回答，否則不在來源討論串中貼任何東西。

## 清理

停止兩個建置，依保留政策移除暫存的設定檔和擷取檔，並在不丟掉使用者工作的情況下，讓 repository 回到原本的狀態。
