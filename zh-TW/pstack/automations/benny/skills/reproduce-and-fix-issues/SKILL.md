# Reproduce and fix issues（重現並修正問題）

在來源討論串中等待一個可信的分類標記。透過目標 app 真實的 UI 重現確切的症狀。當已有修正存在時，驗證它。只有在確認重現之後，才嘗試一次有範圍限制的修正。

載入自動化提供的外部 Benny 設定。如果設定、必要的動作、control 轉接器或完成的功能地圖缺少，就安全地失敗。

## 硬性安全規則

- 在做任何工作之前，凍結來源頻道和根討論串的座標。
- 永遠不要在來源頻道中發根訊息。
- 每次在來源討論串中貼文之前，對來源父訊息做預檢。
- 協調者是唯一的 Slack 貼文者。
- 被委派的分析 worker 是唯讀的，只回傳發現或媒體筆記。
- 修正階段的程式碼 worker，只有在它的環境可證明排除了 Slack 憑證和所有 Slack 寫入動作時才能修改。否則由協調者修改。
- 每個子代理的提示詞都必須明確禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage` 以及所有其他 Slack 寫入。
- 永遠不要給子代理 Slack token、貼文指示、用於貼文的來源座標，或對外回報的權限。
- 如果某個子代理需要 Slack 寫入權限才能執行，就不要啟動它。
- 工具類機器人是證據來源。除非有人明確把修正委派給它們，否則它們不擁有修正。
- 確切、具辨識性的症狀必須透過真實的 UI 互動出現兩次。
- 狀態檢查可以確認一個觀察。它不能注入或強制產生症狀。
- 沒有確認的重現，就不撰寫修正。
- 既有的 PR 或 commit 會把這次執行切換到驗證模式。不要覆寫它們。
- 使用 `github.com` 的 PR 連結。
- 讓擷取畫面、錄影、log 和 token 遠離版本控制。
- 被委派的分析使用 pstack 的 `principle-guard-the-context-window`。
- 在重現、修正和驗證的過程中，套用 pstack 的 `principle-sequence-verifiable-units`、`principle-fix-root-causes` 和 `principle-prove-it-works`。

## 1. 凍結來源座標

在列工作清單或委派之前：

1. 要求觸發的頻道等於設定的來源頻道。
2. 如果有 `trigger.thread_ts`，就把 `SOURCE_THREAD_TS` 設為它。否則使用 `trigger.ts`。
3. 要求 `SOURCE_THREAD_TS` 不為空。
4. 把 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 儲存為不可變的值。
5. 讀取來源討論串，確認它的根訊息恰好有那些座標。
6. 取得來源永久連結。

永遠不要用回覆的時間戳記、維運時間戳記或狀態訊息的時間戳記取代這些值。

每次在來源頻道中貼文之前：

1. 用不可變的座標讀取討論串。
2. 確認父訊息存在、沒有被刪除，而且仍屬於來源頻道。
3. 只用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 送出。
4. 再次讀取討論串，確認新訊息是一則回覆。

如果任何檢查失敗，就什麼都不貼。永遠不要改在根層級或備用頻道重試。

## 2. 等待分類契約

在設定的判定預算時間內觀察來源討論串。等待時保持安靜。

只在以下條件成立時接受判定：

- 它的作者符合 `slack.triage_identity_user_id`。
- 它是 `SOURCE_THREAD_TS` 底下的一則回覆。
- 它包含恰好一個設定的標記。

公開的標記形式：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

只有 `bug` 或 `performance` 時才繼續。擷取選用的追蹤系統網址。遇到 `other`、沒有判定、不可信的作者、互相衝突的標記或逾時，就安靜地停止。

這個標記取代了私有的機器人身分和自由格式的判定比對。

## 3. 套用所有權與修正成品的關卡

在開始工作之前的那一刻，重新讀取討論串。

### 有人明確在修它

當有人明確認領修正、給出具體的實作計畫，或要求另一個 agent 實作、打補丁、修正或開 PR 時，就停下。

以下不算擁有修正：

- 機器人整理證據。
- 工具查詢 log 或工單。
- 有人要求機器人診斷、解釋、檢查或重現。
- 機器人貼出一個原因假設，但沒有同意要實作它。

依被要求的動作判斷，而不是依有沒有機器人在場判斷。

### 已經有修正成品

如果有開啟中的 PR 或已合併的 commit 合理地修正了這份回報，就切換到 `references/verify-existing-fix.md`。

成品可能來自討論串、追蹤系統議題、repository 歷史或 PR 搜尋。沒有 commit 或 PR 的主張不算修正成品。

如果有人擁有這份工作但還沒產出成品，就停下。不要跟他們搶。

## 4. 開一個選用的維運討論串

如果設定了 `slack.operations_channel_id`，協調者可以在那裡建立一則根狀態訊息。這是重現流程中唯一允許的根層級貼文。

把它的座標儲存為 `OPERATIONS_CHANNEL_ID` 和 `OPERATIONS_THREAD_TS`。永遠不要把它們和來源座標混淆。

使用設定的純 Unicode 狀態字串。狀態文字保持簡短：

- 重現中（Reproducing）
- 無法重現（Could not reproduce）
- 受阻（Blocked）
- 已重現（Reproduced）
- 正在驗證既有修正（Verifying existing fix）
- 正在嘗試有範圍限制的修正（Attempting bounded fix）
- 已開草稿 PR（Draft pull request opened）
- 修正沒有落地（Fix did not land）

偏好設定的 Cursor Slack 動作。只有在使用者為了某個狹窄的缺少能力（例如編輯這一則狀態訊息）設定了 `BENNY_SLACK_BOT_TOKEN` 時才使用它。永遠不要把 token 暴露給 worker。

如果沒有設定維運頻道，就把詳細狀態保留在自動化執行的輸出中。不要用來源頻道的根訊息代替。

## 5. 載入並檢查 control 轉接器

讀 `references/control-adapter.md` 和位於 `control.feature_map_path` 的完成地圖，然後呼叫 `control.skill_name` 指名的技能。

找出符合回報中使用者路徑的功能地圖章節。操作 app 之前先讀它。如果沒有任何章節涵蓋這個功能，就把這次執行標為受阻，而不是發明一條路徑或選擇器。

要求以下七項能力全部具備：

1. 啟動設定的目標 app 和測試環境。
2. 瀏覽地圖上的功能並操作它記載的狀態。
3. 用點擊、打字、按鍵、捲動、拖曳、調整大小或導覽來操作真實的 UI。
4. 在不修改狀態的情況下檢查它。
5. 擷取截圖。
6. 開始和停止螢幕錄影。
7. 清理程序、工作階段、設定檔和暫存資料。

如果轉接器不存在，或缺少任何必要的能力，就把維運狀態標為受阻並停下。不要假裝一張截圖、一個單元測試、一次狀態修改或讀原始碼就是 UI 重現。

## 6. 研究回報

讀完整個來源討論串，以及有的話，追蹤系統議題。

蒐集：

- 確切的動作路徑
- 預期行為
- 觀察到的行為
- 兩者分歧時具辨識性的狀態
- 頻率
- 版本、環境和平台
- 附件和錯誤特徵
- 候選的程式碼區域

檢查截圖和影片。有幫助時，用唯讀的平行 worker 處理程式碼歷史、測試點子、影響範圍對應和媒體審查。每個 worker 拿到一個範圍很窄的問題，以及禁止 Slack 寫入的指示。

用 pstack 的 `how` 技能在 repository 中追蹤這個動作。用 `why` 處理退步歷史和防禦性程式碼。形成互相競爭的原因假設，並找出能區分它們的證據。

## 7. 重現

透過 control 轉接器啟動目標 app。

在行動之前，確認 app、工作區、帳號、資料集和功能狀態都是正確的。使用穩定的 app 標記。不要只依賴視窗順序或一個熟悉的標題。

透過真實的 UI 動作操作回報中的路徑。

在宣稱已重現之前：

1. 說出正確的最終狀態。
2. 說出壞掉的最終狀態。
3. 到達它們分歧的那一點。
4. 觀察到壞掉的狀態。
5. 重設足夠的狀態，讓第二次嘗試是獨立的。
6. 重複同樣的路徑，再次觀察到同樣壞掉的狀態。
7. 可以的話，交叉檢查一個真實的狀態值。

預期中的對話框、載入狀態或設定步驟不是 bug。擷取能區分正確與壞掉行為的最終狀態。

使用設定的重現預算。如果在預算內症狀沒有重現，就回報一個乾淨的「無法重現」結果。如果環境無法提供某個必要的能力，就回報「受阻」並說明缺少了什麼。

## 8. 擷取並審查證據

對於成功的重現：

- 錄下通過症狀的完整路徑。
- 擷取壞掉的最終狀態的截圖。
- 存一份簡短的筆記，寫明確切的步驟和觀察到的狀態。
- 把成品放在設定的暫存成品資料夾中。

請一位唯讀的媒體審查者回答一個問題：證據是否清楚顯示了那個具辨識性的壞掉狀態？

如果答案是否或不確定，重現就不算確認。擷取更好的證據，或使用「無法重現」。

有設定維運討論串時，只在那裡貼詳細的證據。來源討論串的更新保持簡潔。

## 9. 回報重現結果

先更新維運狀態。

對於「無法重現」或「受阻」，在來源討論串中什麼都不貼。由維運討論串或執行輸出承載結果。

對於確認的重現，執行來源預檢，並最多貼一則主動的來源回覆：

- 說明問題已重現。
- 有的話，連結維運證據討論串。
- 最多包含三個簡短的發現。
- 有的話，連結追蹤系統議題。
- 預設不通知負責人。

只有在設定的 Slack 動作會把證據留在同一個來源討論串內、而且組織的保留政策允許時，才附上證據。

等待設定的拒絕時間窗。如果有人指出設定或詮釋是錯的，就修正重現一次。在時間窗結束、沒有有效的拒絕之前，不要開始修正階段。

## 10. 驗證既有的修正

當有修正成品存在時，遵循 `references/verify-existing-fix.md`。

驗證必須顯示症狀出現在基準版本上，而在打過補丁的版本上消失。兩條路徑都透過真實的 UI 做兩次。

不要修改既有的修正、加一個競爭的補丁，或開一個替代的 PR。

## 11. 判定是否可以做有範圍限制的修正

只有在以下全部成立時才嘗試修正：

- 結果是單純、確認的重現。
- 媒體審查確認了壞掉的最終狀態。
- 沒有出現既有的修正成品。
- 在拒絕時間窗內沒有人認領修正。
- 執行期證據找出了根本原因。
- 可能的改動符合設定的修正預算和 repository 範圍。
- control 轉接器能同時執行基準版本和打過補丁的版本。

如果任何條件不成立，就保留重現報告並停下，不開 PR。

通過關卡時，把維運狀態更新為「正在嘗試有範圍限制的修正」。

## 12. 找出根本原因並實作

每一則 Slack 貼文、最終的 diff 審查、commit 和 PR 都由協調者負責。

唯讀的 worker 可以：

- 追蹤程式碼和歷史
- 提議測試
- 對應影響範圍
- 審查 diff
- 審查媒體

它們不修改、不執行對外寫入、不貼狀態，也不擁有修正。

只有在工具隔離已從某個 worker 移除 Slack 憑證和所有 Slack 寫入動作時，才能在這個階段把一個範圍嚴格限制的程式碼修改委派出去。它的提示詞仍然必須帶有明確禁止 Slack 寫入的指示。協調者審查這次修改，並執行或驗證必要的測試。如果工具隔離不確定，就讓協調者自己修改。

用執行期證據確認機制。在修改之前排除互相競爭的假設。

用最小、有理由的改動修正根本原因。

- 當有便宜的本機測試目標時，呼叫 pstack 的 `tdd` 技能，在修正前先寫失敗的測試。
- 當路徑昂貴、不清楚或依賴大量整合時，說明為什麼跳過 TDD。
- 不要混入無關的清理。
- 如果改動超出設定的工作量或風險預算，就停下。

## 13. 證明修正

保留原本的基準證據。

在打過補丁的版本上：

1. 跑同一條真實的 UI 路徑。
2. 重複兩次。
3. 顯示壞掉的狀態消失了。
4. 顯示取而代之的是預期的狀態。
5. 擷取修正後的錄影和截圖。
6. 交叉檢查基準時使用的同一個真實狀態值。

編譯、單元測試、程式碼審查或一份看似合理的 diff，都不算修正後的證據。

跑聚焦的測試，然後對改動行為周圍的影響範圍做冒煙測試。涵蓋這次改動可能影響的鄰近狀態、輸入、權限、平台和失敗路徑。如果仍有退步，就停下，不開 PR。

## 14. 開一個草稿 PR

只有在有前後對照的證據之後：

- 審查最終的 diff，確認沒有無關的改動和機密。
- 跑 repository 必要的檢查。
- 在 repository 的工作流程允許時，建立小而有序的 commit。
- 開一個草稿 PR。永遠不要從這個工作流程合併或部署。
- 用追蹤系統支援的 PR 語法連結設定的追蹤系統議題。
- 使用設定的公開網址格式，通常是 `https://github.com/{owner}/{repo}/pull/{number}`。
- 包含重現步驟、根本原因、測試結果、前後對照的證據，以及影響範圍檢查。
- 把 PR 文字和所有 Slack 更新都用 pstack 的 `unslop` 技能處理過。

如果建立 PR 失敗，不要宣稱成功。把 commit 或分支狀態保留在執行輸出中，並把維運狀態標為「修正沒有落地」。

成功時，把維運狀態標為「已開草稿 PR」，並在維運討論串中貼一則附上 PR 連結的簡潔回覆。不要建立第二則來源頻道的根訊息或主動的來源回覆。

## 15. 後續與清理

在一個後續時間窗內觀察設定的維運討論串。

- 用已經蒐集到的證據回答直接的問題。
- 當一個具體的更正讓設定失效時，套用它，並重跑重現一次。
- 不要介入人與人之間的協調和閒聊。
- 被要求時就停止。

一定要呼叫 control 轉接器的清理能力。只在設定的保留政策允許的期間內保留成品。
