# Maintain a verification skill（維護驗證技能）

app 一改變，功能地圖就開始腐壞。這個技能是由 `/create-verification-skill` 產生的技能（或任何附有功能地圖的專案專用驗證技能）的維護迴圈。嚴謹的單位是「功能」，而不是每一句話：從原始碼涵蓋每個功能檔案，並實際操作每個功能，但不需要把每個項目符號都執行到底。

## 結果

選一個，並說明是哪一個：

- **clean（乾淨）** —— 每個功能都有原始碼和即時的涵蓋；沒有值得出貨的東西。不開分支、不開 PR。
- **changed（有改動）** —— 一個 PR 出貨經證實的文件、測試工具或地圖修正。
- **blocked（受阻）** —— 涵蓋檢查無法完成，或一個經證實的修正無法安全出貨。確切說明是什麼擋住了它。

## 修改範圍

只修改驗證技能自己的資料夾（它的 SKILL.md、features/，以及它擁有的任何測試工具腳本）。執行期間永遠不要修改產品程式碼：地圖描述了、但 app 已經不再做的行為，要嘛是文件偏移（修正地圖），要嘛是產品退步（回報它，不要在文件中掩蓋它）。

## 檢查流程

0. **找到目標。** 找出要維護的驗證技能：內文有啟動/操作章節和功能地圖的專案專用技能（通常是 `.cursor/skills/verify-*/`）。有好幾個候選 → 問是哪一個；一個都沒有 → 停下，並指向 `/create-verification-skill`，而不是捏造一個目標。

1. **索引衛生。** 讀功能地圖的 README，並 glob 它旁邊的檔案。修正缺少、多餘、重複或失效的項目。保持輕量；不要產生清單。

2. **原始碼波次。** 每個功能檔案一個唯讀子代理，同時啟動。每個子代理從原始碼解釋「這個面向使用者的功能是怎麼運作的？」，附出處標出可能的文件偏移，並回傳一份精簡的即時驗證做法。子代理永遠不操作 app，也永遠不修改檔案。回傳格式：功能摘要 / 原始碼進入點 / 可能的偏移或無 / 一份做法。

3. **調和。** 每個功能檔案都有回傳的摘要。把重疊的做法合併成盡可能少的 app 狀態。抽查被引用的偏移；不要重新證明乾淨的主張。掃過最近的變動，找出地圖中缺少的面向使用者介面——在說某個東西缺少之前，要有具體的原始碼路徑。

4. **即時檢查。** 即使原始碼看起來很乾淨也必須做。所有操作都由協調者負責；遵循驗證技能自己的啟動模式——伺服器和 UI 是一個長期存在、依序操作的實例，短命的 CLI 則是每次操作一個全新的隔離工作階段（由技能的 Launch 章節決定，不是這裡）。每個功能至少操作一次，並在整個檢查過程中守住三個不變條件，不管發生什麼失敗：(1) 永遠不要操作一個「自從上次發生意外之後還沒做過健康檢查」的實例——第一次操作前做 doctor，在以工作階段為單位時每個新的工作階段都做 doctor，任何操作失敗後再做 doctor；而當 doctor 看不到失敗時（健康的程序上卡住的 UI 狀態），重設到已知狀態或重新啟動，而不是祈禱；(2) 到目前為止擷取的證據在每次清理後都要存在，要在它指定的位置檢查，而不是假設；(3) 一次操作啟動的任何東西，在那次操作不再有用之後就不該留存——不論工作階段是卡住、已結束還是共享的，失敗迭代的殘留物都要清掉（共享實例的話，清掉殘留物，而不是實例本身）。由技能偏移造成的 doctor 失敗就是偏移：在修改範圍內修正它並重試一次——只重啟被修正弄失效的東西，其他不動——之後才能把這次檢查判為 `blocked`。一個無法到達的功能，只有在附上具體的前置條件（認證、權限、作業系統、外部狀態）和嘗試過的路徑時，才能標為 `verified-unreachable`（已驗證為無法到達）；如果地圖漏掉了那個前置條件，那就是偏移。分類中產生的任何測試工具修正，在出貨前都要重新實際操作一遍。最後的拆除在本次執行的最後一次操作（包括那些重新證明）之後進行，讓任何東西都不會比這次執行活得更久（依技能規定，證據要保留）。

5. **分類。** 錯誤或缺少的使用者視角描述 → 文件偏移，修正它。行為正常但測試工具無法操作 → 測試工具缺口，修正它；測試工具的修正遵循和產生時相同的 helper 規則（腳本可執行、在技能內文中記錄呼叫方式）。app 的行為真的壞了 → 產品缺口；為使用者記錄下來，不要放進這個 PR。

6. **出貨或停止。** changed 的話：一個經證實的修正 PR，先重讀每個改過的檔案。clean 或 blocked 的話：不開 PR，誠實回報結果和涵蓋範圍。

在暫存位置保留精簡的執行筆記（涵蓋的功能、無法到達的前置條件、確認的偏移、結果）；不要提交它們。
