### Autopilot-full（全自動駕駛）

**你負責判定，永遠不負責 PR。每個 PR 由一個負責人從建構帶到合併；在從未寫過這段程式碼的 swarm 證明了要落地的程式碼之前，什麼都不會合併。**

一個判定涵蓋一份 patch，CI 全綠涵蓋一個 head。第 4 步只跑一次完整的 swarm，只有重大改動時才再跑一次。`playbooks/shipping.md` 中的 patch-id 規則可以讓某條檢查線的結果延續下去，而每個新的 head 都需要它自己的 CI 全綠。

1. **操作者的關卡優先。** 授權只涵蓋佇列中的項目，所以操作者指明屬於自己的項目，以及佇列以外的 PR，都停在可合併狀態。要求說明計畫不等於同意執行。
2. **每個 PR 派一個負責人，並把它的工作放在替代者找得到的地方。** 為整個計畫決定一次代碼平台。預設是 GitHub CLI（`gh`）。如果 `command -v origin` 成功、而且 Origin 能解析這個 repository，所有 PR 操作都用 `origin pr`。否則留在 `gh` 並記錄這個備案。永遠不要要求 Graphite（`gt`）。每個負責人都是一個 Cursor 雲端 agent，它負責建構、依 `playbooks/opening-a-pr.md` 開 PR、在真實成品上證明改動、依 `playbooks/babysit.md` 看顧到全綠，並在第 4 和第 5 步放行後合併。

   及早開 PR，讓 CI 和機器人跟工作同步執行。只有在清除垃圾內容（`cursor-team-kit` plugin 的 `deslop` 技能（`/deslop`））和 `/no-comments` 之後，程式碼才算就緒，這樣完整的 swarm 才會在完成的程式碼上執行。然後 rebase 到目前的主線，並在自我證明之前回報程式就緒的 head，讓驗證在 patch 要落地的基底上執行。之後的每個 head 都要回報，自我證明、CI 和 babysit 完成後回報可合併。修正回合保持在那個基底上，除非主線發生衝突、弄壞 CI，或落地了一個已知會碰到相同檔案的並行改動，因為每次 rebase 都會讓 CI 重跑。在程式就緒的推送前，以及之後需要驗證者的推送前，在已提交的 head 上對改到的路徑跑 repo 的檢查。

   假設虛擬機會掛掉。開始後不久，就推送，並依 **show-me-your-work** 技能在根代理的 store（路徑在系統提示詞中）開始一份決策紀錄，然後每完成一個單元就推送，再開始下一個。派出子代理的人要在那個 store 記錄它的 id、狀態，以及根據同類過去執行得出的「超過這個時間就算卡住」的執行時間，這樣父代理掛掉時根代理也能探查它。只 force-push 你自己的分支，並用 `--force-with-lease` 鎖定在你上次推送或接手的 SHA；遇到任何不是你做的推送，停下並回報給根代理。
3. **負責人從主線平行執行，永遠不堆疊**，讓每個 PR 都能獨立落地。
4. **只做一次 swarm 驗證。** 完整的 swarm 在程式就緒的 head 上跑一次。只有新行為、重新設計或大量新 diff 才會再跑一次完整的 swarm。rebase、合併衝突的解決或小修正，在新 head 上由單一驗證者檢查；只改措辭的改動則不需要。依 **swarm** 技能，在程式就緒的 SHA 上分派彼此獨立的驗證者。它們重跑關卡、透過真實介面的 control 技能（例如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）或一個指定的驅動程式即時證明承重的行為，並稽核 diff。沒有即時檢查線，或在你稽核可合併報告的收據之前，判定都不算乾淨，因為沒有任何檢查線會相信它沒檢查過的主張。

   只為你能展示的問題擋下 PR：在 head 上失敗的執行，或被這個 PR 弄錯的文件行。PR 的基底（不論是主線還是堆疊中它下面的 PR）原本就有的問題不會阻擋，除非這個 PR 複製了它或新觸及它。只有使用者會碰到的 bug、失敗的關卡或出貨的錯誤文件會阻擋，其他一切放進後續工作。
5. **負責人只合併你驗證過、並在它要落地的主線上測試過的東西。** 光是 CI 全綠永遠不能授權合併。一旦 swarm 的檢查線開始執行，合併準備就是 rebase 到目前的主線、回報新的 head，並等 CI 全綠。

   合併前一刻，抓取主線，並判斷它的改動是否會影響這份 patch，因為每次主線前進就 rebase 是永無止境的。當要落地的程式碼從未被測試過時，就 rebase 並等 CI，例如發生衝突、雙方都改了同一個檔案，或改變了 PR 會跑哪些檢查。雙方都改了的 lockfile，如果在合併結果上做凍結安裝能通過、而且 PR 改動的套件在那裡的解析結果和在 head 上一樣，就不需要 rebase，因為那次安裝已經測試了將要落地的 lockfile；安裝失敗則代表 rebase 必須修好它。當主線改了 patch 的呼叫者或 patch 依賴的東西（例如它呼叫的程式碼或某個相依版本）時，在合併結果上跑 patch 的檢查，通過就合併。否則就直接合併。如果主線會迫使在合併準備之後做第三次 rebase，就暫停並回報給根代理，由它安排相互衝突的工作的順序。
6. **執行根層的職責。** 任何放寬關卡的事情，例如提高預算或加入允許清單，都需要驗證者的證明，以及你重新的副署，因為想要全綠的正是負責人。在涵蓋核准的授權之下，那個副署就是核准，負責人對它的紀錄會指向你的副署，讓檢查線去核對。被停用或被設為軟失敗的檢查一律要拿出來，因為它不再守護每個情況。永遠不要給予或繞過代碼平台強制要求的核准，因為沒有任何副署能涵蓋它。

   在操作者同意後，啟用 `/loop 1h` 持續稽核，直到沒有委派中的工作為止，因為長時間執行會偏移，agent 也會默默卡住。每個 tick 都從主線重新讀這份劇本並修正偏移，例如未回報的 head 或未記錄的 agent，做法是讓它的負責人記錄下來，因為偏移是紀錄上的缺口，不是卡住。它會探查每個 agent，一直到最末端的檢查線，並依各自造成的實際效果判斷，因為狀態文字和摘要可能掩蓋卡住的子代理。一個 agent 出錯、無法開始回合，或超過它的卡住時間仍沒有任何新東西時，就算卡住；到第一個 tick 時既沒推送、也沒寫過任何紀錄列的負責人也算。在等你或操作者回應的 agent 不算卡住，所以去回應它。立刻替換卡住的 agent，不必等它的停止生效。對操作者有改變的 tick，最後依 **ketchup** 技能幫他們跟上進度；沒有改變的 tick 則保持安靜。
7. **操作者喊停時立刻停手。** 暫停命令會以「零寫入」的指令送到每個負責人。每個負責人回報自己的進度，並保留任務說明，直到操作者解除暫停。

**回覆：** 依 **ketchup** 技能幫操作者跟上進度，涵蓋每個 PR 的狀態與判定、合併了什麼、副署及原因、待處理的操作者關卡，以及停放的後續工作，並附上每個 PR 和紀錄的連結。
