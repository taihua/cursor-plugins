### Bug fix（修 bug）

**這個任務由你負責。規劃、審查、驗證。** 把調查和修正委派給子代理，自己保持主導。依「子代理」章節，為每個子代理選擇工作需要的推理等級與快速或標準速度。

要科學。每一行出貨的程式碼都要能追溯到執行期證據。「可能有幫助」的雙重保險是假設，不是修正，不能出貨。當證據推翻一個假設時，還原因它而做的改動。只出貨證據所能支持的最小改動，不多做。

1. 透過 control 技能（見「不可妥協的規則」）在對應的介面上自己重現，即使某個除錯或埋點流程說要請使用者重現。只有在你能具體說明 control 介面無法觸及目標的理由，而且已經盡可能操作到極限之後，才請使用者協助。如果無法直接重現，就合成觸發條件、收緊條件，或埋點直到它發生。
2. 用二分法找原因。列出候選假設，再逐一排除直到只剩一個。用 `how` 檢視受影響的子系統、用 **why** 技能查看回歸歷史，作為假設的起點。每一輪選擇能砍掉最多剩餘問題空間的切分點，取得執行期證據，排除。當程式狀態不清楚時，加入埋點或 log，在程式執行時讀它。不要猜。漫長或頑固的追查用 Cursor 的 `/loop` 指令推動。在第 3 步的 architect/interrogate 分派之前，先用執行期證據確認存活下來的**機制**。
3. 規劃修正。如果跨越函式邊界，先用 `architect`。用你設定的 bug-fix 模型（預設 `grok-4.7-xhigh-fast`），以明確的範圍把實作委派給子代理。
4. 在同一個介面上驗證。原本的重現現在通過了。「無法判定」或量錯介面都不算通過，要標示出來。單元測試顯示的是分支行為，不是 bug 不存在。
5. 安排 commit 的順序，讓失敗的重現在 git 歷史中比修正先落地。當 bug 有便宜的本機測試路徑時，參考 **tdd** 技能「先寫失敗測試」的節奏。當測試成本高、依賴大量整合或不清楚時就跳過。
   這就是 **sequence-verifiable-units** 原則技能的標準範例：先有失敗的測試，修正疊在上面。
6. 執行 **Opening a PR**。

**回覆：** 什麼壞了、根本原因、修正、你如何驗證。逐字貼上先失敗後通過的重現輸出。
