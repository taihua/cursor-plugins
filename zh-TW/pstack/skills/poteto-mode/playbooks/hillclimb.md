### Hillclimb（爬坡優化）

**指標與實驗的完整性由你負責。監督並審查，把嘗試委派出去。** 用於針對目標持續、反覆地改善一個可量測的東西。一次性的修正是 Bug fix 或 Perf issue。這是迴圈。

核心紀律：一個改動、一次量測、保留或還原。永遠不要堆疊未經測試的改動，也永遠不要從讀程式碼就宣稱有改進（**prove-it-works** 原則技能）。

1. 選定指標前，先掌握工作負載和架構。對目標跑 **how** 技能，說出會影響結果的真實工作負載面向（資料大小、歷史、狀態、並行程度），並選一個能重現使用者抱怨的案例。如果沒有案例能重現，先修好重現，而不是爬坡。然後固定一個指標、哪個方向算更好，以及一個可檢查的停止判定式：它要同時有目標和最少嘗試次數，這樣一次早期的幸運勝利不會結束這次執行（例如「比基準好至少 50%，且至少 10 次迭代」就是這種形式）。使用者有給數字就用使用者的，否則要先取得共識。
2. 建立量測工具、證明它的靈敏度，然後凍結它（**build-the-lever** 原則技能）。跑幾種對比鮮明的真實工作負載，確認目標案例能重現症狀，而較容易的案例如預期般區分開來。如果工具無法區分它們，就修改工作負載或指標。凍結前用 **benchmark-checklist** 技能檢驗這個工具，並讓它印出錯誤數量和完成的工作量。凍結後，一個可重複的指令就能輸出指標，並且取樣次數足以壓過雜訊（N 次的中位數，而不是單次執行）。在任何改動之前，記錄基準指標，以及回歸關卡（必須持續通過的測試）的一次全綠執行。
3. 透過 **show-me-your-work** 技能開啟決策紀錄。一個 `decision.tsv`，每次嘗試一列：id、假設、改動、改動前、改動後、差異、測試、判定（保留或還原）、備註。每次嘗試前先讀它。不要放進程式碼樹（加進 gitignore）。
4. 讓每個假設都以第 1 步的架構模型為依據，說出具體的機制（「把 X 移出啟動路徑，因為它阻擋了首次繪製」），而不是「試著 memoize 某個東西」。效能指標的話，依 Perf issue 劇本（`playbooks/perf-issue.md`）第 2 步的效能箴言為假設排序。只借用它們的順序，不借用那一步的停止規則。
5. 迴圈，每次迭代一個假設：
   - 用你設定的 hillclimb 模型（預設 `grok-4.7-xhigh-fast`）以緊縮的範圍把改動交給子代理。依「子代理」章節，為每個子代理選擇工作需要的推理等級與快速或標準速度。監督並審查 diff，而不是自己打字（**guard-the-context-window** 原則技能）。當有好幾個獨立的假設同時成立時，把它們分派給平行的子代理，每個在自己的 worktree 中（**separate-before-serializing-shared-state** 原則技能）。
   - 用凍結的量測工具量測前後，並跑回歸關卡。
   - 只有當指標的變化超過雜訊、且關卡保持綠燈時才接受。否則完整還原這個改動。「可能有幫助」的微調不保留。
   - 每個被接受的修正一個 commit，只暫存你改過的檔案（`git add <files>`，永遠不要用 `-A`）。不論保留或還原，都記錄那一列。
   每次迭代都以一次檢查結束，再開始下一次（**sequence-verifiable-units** 原則技能）。如果這次執行無人看管，只借用 Autonomous run 劇本（`playbooks/autonomous-run.md`）的喚醒機制，不借用它的停止規則。
6. 突破第一個停滯期。停滯時（連續好幾次被拒絕），轉換類別、組合差一點成功的做法、重讀原始碼，或在斷定已經爬到頂之前試試更激進的東西。正確性和簡潔性比數字更重要。還原會破壞行為的改進，保留能維持數字的簡化（**laziness-protocol** 原則技能）。
7. 判定式達成時，或剩下的點子邊際效益太低、不值得付出成本時停下。不要為了達成而放寬判定式，也不要在還有便宜、未試過的假設時就放棄。如果卡住了，就呈報出來，而不是空轉。
8. 執行 **Opening a PR**，被接受的 commit 依落地順序堆疊。

**回覆：** 指標與目標、從基準到最終值及百分比差異、執行的迭代次數（保留 vs 還原）、每個被接受的修正各一行、`decision.tsv` 路徑，以及如果要再推進，你下一個會試的最好點子。
