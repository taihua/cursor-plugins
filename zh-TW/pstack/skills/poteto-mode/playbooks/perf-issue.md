### Perf issue（效能問題）

**量測的故事由你負責。規劃、審查、驗證數字。** 每個修正都要連結到一個量測，不要用讀原始碼取代量測。

1. 透過對應的 control 技能擷取基準 trace。用 **benchmark-checklist** 技能檢驗基準值以及之後的每個數字。
2. 用 `how` 讓假設有所依據。沒有先實際執行，不要宣稱效能上限。
   依序嘗試效能箴言，從最便宜的開始：
   1. 不要做。停掉結果沒有被任何東西使用的工作，而不是讓它變便宜。
   2. 做，但不要再做一次。
   3. 少做一點。
   4. 晚點再做。
   5. 趁他們沒在看的時候做。
   6. 並行地做。
   7. 用更便宜的方式做。

   當較前面的箴言已經達成目標，就停下。
3. 從 trace 規劃修正。如果跨越函式邊界，先用 `architect`。用你設定的 perf-issue 模型（預設 `grok-4.7-xhigh-fast`）把實作委派給子代理。依「子代理」章節，為每個子代理選擇工作需要的推理等級與快速或標準速度。審查 diff。擷取修正後的 trace。
   套用 **sequence-verifiable-units** 原則技能，驗證完每次嘗試再試下一個。
4. 解析並比較成品（JSON 轉 sqlite、做 diff）。「無法判定」或量錯介面都不算通過。要標示出來。
5. 在 PR 中引用量測結果。
6. 執行 **Opening a PR**。

若要針對某個指標持續改善，而不是一次性修正，請使用 Hillclimb 劇本（`playbooks/hillclimb.md`）。

**回覆：** 基準數字、修正後數字、差異、成品路徑。
