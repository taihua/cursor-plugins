### Multi-phase or multi-PR plan（多階段或多 PR 計畫）

**你負責計畫，不負責程式碼。計畫是一份檢查清單，由負責人一格一格執行，操作者則根據證據稽核。** 計畫就是交付物。不要實作。

1. 當改動只有一兩個檔案、做法很明顯時，跳過計畫。說明這一點並停下。
2. 動筆前，依 `playbooks/prototype.md` 用原型解決未決的問題。只有在沒有任何執行能解決的產品或偏好判斷時才問操作者。
3. 撰寫計畫檔案。開頭寫明改了什麼、依落地順序排列的 PR id，以及相依關係圖：哪些 PR 彼此獨立、從主線開分支，哪些要等哪些，以及每個 PR 可以碰的檔案。接著每個 PR 一節。一個 PR 是一個帶有自己證據的改動（**sequence-verifiable-units** 原則技能）。每一節都有格子，寫明它依賴什麼、它修改的檔案、它建構的那一個改動、你會看到的結果，以及它的驗證。
4. 光靠測試不足以構成驗證。只有當一個 PR 的 unit（單元）、live（即時）和 perf（效能）格子都打勾時，它才算驗證過。每個即時格子都用一個具體情境和一個通過判定式操作真實介面。效能格子寫明指標、探測、先量測的主線基準，以及判定失敗的數字。改變互動的 PR 要等操作者審查後才能合併。
5. 交回計畫路徑，然後停下。執行要等操作者明確同意後才開始。

**回覆：** 計畫路徑、PR id 及其相依關係和需要審查關卡的集合，以及什麼仍未被證明。
