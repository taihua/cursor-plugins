# Bugbot triage（Bugbot 留言分類）

當 Babysit 劇本（`../playbooks/babysit.md`）處理 Bugbot 或自動化審查的留言時，使用這份參考資料。目標不是預設忽略 Bugbot，而是不再把每一則留言都當成必須修改程式碼。

## 判斷標準

採取行動前，先為每個 Bugbot 討論串分類：

- `fix`（修正）：留言指出一個合理可能存在的正確性、安全性、隱私、資料遺失、認證、計費、遷移、冪等性、競態條件或已出貨行為的問題。在擁有該程式碼的最低 PR 中修正，然後回覆 commit SHA 並解決討論串。
- `dismiss`（駁回）：留言符合一個已記錄的低風險雜訊模式，而且目前的程式碼/脈絡證明這個疑慮不需要修改程式碼。用簡短理由回覆並解決討論串。
- `ask`（詢問）：留言是全新的、高嚴重度的、與安全/隱私/資料相關，或有歧義。問使用者，不要用猜的。

有疑慮時就問。跳過一則吵雜的程式碼品質留言成本很低；跳過一個真正的資料或安全 bug 則不然。

## 已學到的模式的格式

未來新增的模式依這個格式：

```markdown
### <簡短的模式名稱>

- Confidence: candidate | recurring | strong
- Skip when: <必須成立的條件>
- Do not skip when: <風險界線>
- Example signal: <能辨識這個模式的字句或程式碼脈絡>
- Source: <PR/留言網址或簡短的歷史說明>
```

只有一兩個例子時用 `candidate`（候選）。經過多次真實駁回後用 `recurring`（反覆出現）。只有在模式範圍很窄、多次驗證過、而且低風險時才用 `strong`（強）。

## 反覆出現的可跳過候選

### 刻意的 UI 或設計系統視覺改動

- 信心程度：candidate
- 可跳過時機：PR 描述、截圖、設計審查或附近的程式碼明確表示這是視覺改動，而 Bugbot 留言只是在重述某個共用的視覺預設值改變了。
- 不可跳過時機：留言指向無障礙、焦點可見性、鍵盤導覽、色彩對比，或某個 PR 並未刻意改變的元件 API 契約。
- 範例訊號：關於焦點外框、按鈕大小、間距或共用元件視覺預設值的留言，而擁有者回覆「intentional」或「intended」（刻意的）。

### Bugbot 看不到的上層或堆疊內部用法

- 信心程度：candidate
- 可跳過時機：Bugbot 標記某個 export、元件、helper 或檔案未被使用，而目前代碼平台的 PR 清單與 diff、上層堆疊的 diff 或 PR 脈絡顯示它被堆疊中後面的 PR 使用。
- 不可跳過時機：目前的 PR 不屬於堆疊、該符號是公開 API，或所謂的上層用法無法被驗證。
- 範例訊號：「Exported component is never used」（匯出的元件從未被使用），而人類回覆「used upstack」（上層有用到）。

### 平行實作期間的暫時重複

- 信心程度：candidate
- 可跳過時機：PR 刻意重複一小段程式碼，讓新路徑和一條正在被刪除、取代或驗證中的舊路徑平行存在。
- 不可跳過時機：重複的程式碼改變了安全、計費、資料存取、API 行為，或一個長期共用的抽象明顯能降低風險。
- 範例訊號：「Significant duplication」（大量重複）或「duplicated validation logic」（重複的驗證邏輯），而擁有者解釋舊路徑之後會被刪除，或重複的邏輯是刻意保持在局部的。

### 既有的框架或元件不變條件已涵蓋這個警告

- 信心程度：candidate
- 可跳過時機：這個疑慮已經被一個共用元件、框架契約、型別不變條件，或在目前 diff 或附近程式碼中可見的單一真實來源所保證。
- 不可跳過時機：不變條件只是被假設而沒有被強制、依賴時序，或跨越了值可能分歧的非同步/狀態邊界。
- 範例訊號：當共用的 popover 已經強制限制在視窗範圍內，卻有留言說內層 popover 缺少 max-height；或者本地檢查的值和傳入的值來自同一個來源，卻有留言說它可能為 null。

### 擁有者宣告的後續工作或延後清理

- 信心程度：candidate
- 可跳過時機：PR 擁有者明確表示這個問題是已知的後續工作、目前的 PR 沒有讓行為變得更糟，而且留言不是關於高風險區域。
- 不可跳過時機：agent 在沒有擁有者意見的情況下行動、問題是中/高嚴重度的產品行為，或延後會合併一個新的退步。
- 範例訊號：「I'll worry about that later」（我之後再處理）或「we'll delete this eventually」（我們最後會刪掉這個）。

### 自行撤回或明確為誤報的規則留言

- 信心程度：recurring
- 可跳過時機：留言內文或之後的 Bugbot 回覆明確表示該發現已撤回、符合規定或為誤報，而且 agent 能在本機驗證相關規則。
- 不可跳過時機：唯一的證據只是某個人在高風險問題上說「誤報」而沒有解釋。
- 範例訊號：一則檔案命名規則的留言，其內文說明該檔案已經符合規定。

## 預設要詢問的類別

即使之前的 PR 駁回過類似的東西，也不要自動跳過這些類別：

- 安全、隱私、認證、計費、資料保留、訓練資料和權限邊界相關的發現。
- 高嚴重度的發現。
- 遷移、schema、冪等性、並行和跨系統行為的發現。
- 建議的修正很小、而且在不改變產品意圖的情況下明顯能降低風險的留言。

歷史資料顯示，人類有時會駁回安全/資料流相關的留言。把那些當成擁有者的個別判斷，而不是全團隊的跳過規則。

## 近期 babysit 得到的候選心得

在 babysit 期間或之後，當某個心得看起來對團隊有用但還不成熟時，就加在這裡。當好幾個 PR 都確認了某個模式後，優先把反覆出現的候選提升到上面的章節。

### 手動重新實作原生瀏覽器行為

- 信心程度：candidate
- 可跳過時機：幾乎從不。當 diff 用手動的等價物取代原生瀏覽器行為（原生 sticky → JS 定位的複製品、原生捲動目標 → 轉發 wheel/touch 事件、繪製順序遮擋 → mask/clip-path）時，Bugbot 對這類程式碼的邏輯 bug 發現一直都是成立的。
- 不可跳過時機：發現涉及這類程式碼中的事件轉發缺口（wheel deltaMode、觸控平移、邊緣的捲動鏈、點擊容差）、mask/clip 的點擊測試分歧，或 observer 與 React 狀態之間的時序競態。預設修正。
- 範例訊號：「masks do not affect hit-testing」（mask 不影響點擊測試）、「overlay blocks wheel scroll」（覆蓋層擋住滾輪捲動）、「ignores deltaMode」（忽略 deltaMode）、「runs in the IntersectionObserver callback before React applies state」（在 React 套用狀態前就在 IntersectionObserver 回呼中執行）。
- 來源：一個 sticky 遮擋的 PR：六輪 Bugbot、約十八個發現，每一個都被修正而不是駁回。

### 契約測試偏移的主張很容易驗證——先跑測試

- 信心程度：candidate
- 可跳過時機：永遠不要跳過驗證本身，它只要一個指令。當 PR 附帶一個固定協議或文件文字的契約測試（對 SKILL.md 的正規表達式、文件措辭的快照），而 Bugbot 主張「測試不再符合文件」（或反之）時，在分類之前先在 PR 頂端跑那個測試。紅燈從實際上證實了這個主張；綠燈則是駁回回覆中具體的反證。
- 不可跳過時機：不適用——這是驗證捷徑，不是駁回模式。注意，「多輪之後傾向駁回」的經驗法則在這裡會失準：固定文字的測試之所以會偏移，正是因為之前的修正回合改了文字。
- 範例訊號：在一個先前的修正 commit 改寫了被固定段落的 PR 上出現「Contract test omits the pre-fix wait」（契約測試漏掉修正前的等待）；在頂端跑測試，正好在被引用的斷言上失敗。
- 來源：一個有八輪 Bugbot 的固定文字 PR；儘管之前每一輪都已修正並解決，這個主張在第 7 輪仍然是真的。

### 已在同一個 PR 後面被修好的過時安全審查發現

- 信心程度：candidate
- 可跳過時機：agentic security review（或類似工具）主張缺少某個授權/驗證呼叫，而目前的 PR 頂端明顯包含那個確切的關卡（附有測試），通常是在審查執行之後的強化 commit 中加入的。
- 不可跳過時機：被引用的 helper 對所討論的主體來說是 no-op、檢查在它所保護的副作用之後才執行，或缺少對所主張主體的測試覆蓋。
- 範例訊號：一則 HIGH 等級的「missing authorization check」（缺少授權檢查）發現，而確切的防護在頂端已經於副作用之前被呼叫。
- 來源：一個 webhook 端點的 PR，它的強化 commit 晚於審查執行。

### 放寬一個刻意狹窄的錯誤條件會掩蓋真正的錯誤

- 信心程度：candidate
- 可跳過時機：發現要求把一個狹窄的錯誤條件（特定的 `errno`、錯誤代碼或狀態類別）放寬成全部捕捉，而那個狹窄性編碼了真實的區別。典型的形狀是以 `ENOENT` 為條件的相依備案：「執行檔沒有安裝」和「指令執行了但失敗」是不同的情況。對任何非零結束碼都重試，會讓一個合理的失敗（找不到、認證過期、網路）在備案上重跑，然後回報備案的錯誤，把真正的錯誤藏起來。
- 不可跳過時機：狹窄的條件漏掉了同一類別中的情況（另一個「執行檔無法使用」的 errno，例如 `EACCES`，或另一種傳輸層失敗）、未處理的路徑會遺失資料或留下部分狀態，或者重試是冪等的、而且原本的錯誤仍會被呈現。
- 範例訊號：「only retries when X fails with ENOENT … never tries the fallback even when a working Y exists」（只有在 X 以 ENOENT 失敗時才重試……即使有可用的 Y 也從不嘗試備案），指向的程式碼的備案是為了缺少的相依，而不是失敗的操作而存在。
- 來源：一個 CLI 改名的 PR，它的備案是為了缺少的執行檔，而不是失敗的指令而存在。
