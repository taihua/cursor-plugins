> 譯註：這份標準是針對**英文**技術寫作設計的（STE 是「簡化技術英文」，Global English 是「讓非母語讀者也能讀懂的英文」）。部分規則（冠詞、-ing、序列逗號）是英文特有的，但大部分精神——一句一個意思、說誰做了什麼、避免歧義——也適用於中文寫作。

# Technical writing（技術寫作）

寫到讓一個疲憊的工程師第一次讀就懂。

- 刪掉每一個沒有作用的字。
- 用簡短的日常用字：用「use」，不用「utilize」。
- 當某條規則讓句子變差時，用別的方式修正句子，或者不要動它。
- 寫出真實的符號、檔案、旗標或指令名稱，而不是同義詞或對它的描述。
- 不要發明術語。用開發者會說出口的字。一個有名稱的模式，第一次出現時要說明它的意思。

## 變化節奏

- 混合句子長度。拆開承載兩個想法的句子，保留承載一個想法的長句。
- 在解說（explanation）中表達觀點。參考資料（reference）保持乾燥。
- 要具體。不要寫「schema 改動可能會造成問題」，要寫「欄位改名會讓建置失敗」。

## 先選模式（Diátaxis）

一份文件，一種模式。不要混合模式，改為拆開並連結。

- **教學（tutorial）：從做中學。** 說明學習者會做出什麼。每一步都產生可見的結果，而且你要告訴他們應該看到什麼。解釋只給一個子句加一個連結。
- **操作指南（how-to）：達成目標的步驟。** 解決讀者的問題。假設讀者有能力。只有行動。允許分岔。用任務為指南命名。
- **參考資料（reference）：供查閱的事實。** 只描述。要乾燥、完整、篤定。鏡像被描述事物的結構。
- **解說（explanation）：理解與原因。** 一個有邊界的主題。給出脈絡：設計決策、歷史、限制、替代方案。觀點只在這裡被允許，其他地方都不行。

## 對讀者寫句子（Google 開發者風格）

- 用「你」對讀者說話，使用現在式。
- 說出誰做了什麼。只有在動作者未知或無關緊要時，被動語態才沒問題。
- 把指示寫成命令句。把條件放在指示之前，常見的情況放在最前面。
- 不用流行術語、不用比喻性語言、不用「請」，在步驟中永遠不要說「簡單地」、「很容易」或「很快地」。
- 不要預告，也不要讓連續的句子以同樣的片語開頭。
- 用能說明連結去向的文字做連結。
- 標題承載重點，使用句首大寫。每頁一個 h1，不跳過層級。
- 順序用編號清單，其他一律用項目符號。用一個完整的句子引入清單。讓項目保持平行。
- 程式碼用程式碼字型。UI 元素用粗體。使用序列逗號（serial comma）。不寫「etc.」。

## 讓陳述一次載入一個（STE 規則）

- 每個句子一個指示。其他地方每個句子一個想法。
- 拆開超過約 20 個字（英文單字）的指示，以及超過約 25 個字的其他句子。
- 把警告或條件放在它所保護的步驟之前。
- 保留「the」和「a」。
- 給每個字一個意思，每個動作選一個字。
- 把步驟寫成直接的命令句，永遠不要寫成敘述，也永遠不要用被動語態。
- 能避免就避免「-ing」字。

## 不留任何有兩種讀法的句子（Global English）

- 讓「only」和「not」這類字緊鄰它們修飾的字。
- 拆開長串的名詞。
- 讓每個「it」、「they」和「this」都指向一個明顯的東西。永遠不要用「this」或「which」指向整個子句。
- 不要省略動詞，也不要省略顯示結構的小字，例如「that」。
- 當重複冠詞能避免誤讀時，在一串項目中重複它。說清楚「and」或「or」連接的是哪些部分。
- 用句號，不用分號或長破折號。不用斜線，也不用「(s)」。讓括號中的文字是一個完整的文法單位。
- 每個東西在所有地方都用同一個名稱。
- 跳過慣用語、口語、拉丁文縮寫和比喻。

## 語氣與 repo 特定事項

- 對這個技能碰到的每份文件套用 **unslop** 技能。那個技能擁有垃圾模式的目錄：AI 詞彙、填充詞、保留語氣、格式上的痕跡。
- PR 描述和 commit 訊息也是寫作。除了 Diátaxis 以外的每一層都適用於它們。PR 內文是一份審查者一分鐘內就能讀完的簡報。不要貼上 swarm log、SHA 清單或指標表格，用連結。
- 產品 UI 字串不是文件。那些要用你產品的文案指南。
- 程式碼片段用 tab 縮排。寫真實的路徑。讓每個數量或樹狀結構的主張在落地它的那個 commit 上都是真的，並附上能重新產生它的指令。
