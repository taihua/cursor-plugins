# Prompts worth copying（值得複製的提示詞）

換上真實的路徑、技能和完成檢查。隨性的措辭也可以。

> 譯註：以下提供中文版本，可以直接複製使用；斜線指令照打英文。

## 理解

- `/poteto-mode 讀 <討論串>。用你自己的話、用白話複述根本問題。`
- `/in-your-own-words <又長又亂的要求>`
- `/sharpen <你正要送出的提示詞>`
- `/poteto-mode 調查為什麼 <症狀>。告訴我目前知道什麼、你用了哪些資料、以及你最可能的假設。先不要改任何程式碼。`
- `用 /how 了解 <子系統>。然後用 /why 找出它最近為什麼壞掉。`
- `/recall 我上週在 <主題> 上的工作，然後讀 <議題>。`
- `/teach 教我你為什麼這樣實作，而不是 <另一種方式>。你做了什麼取捨？`
- `/poteto-mode 接手這個分支。讀決策紀錄，找出完成了什麼，然後繼續。不要重做已完成的工作。`

## 建構

- Bug：`/poteto-mode <症狀>。先重現，再修好並驗證。`
- app 中的 bug：`/poteto-mode 用 /verify-<app> 重現這個。如果在 main 上能重現，就修好它並給我影片作為證據。`
- 有便宜測試的 bug：`/poteto-mode 先重現 <bug>。如果有便宜的測試路徑，就用 /tdd。然後修正並重跑。`
- 新功能：`/poteto-mode 加上 <行為>。<目前的輸出> 要一個位元組都不變。兩者都要驗證。`
- 重構：`/poteto-mode 把 <程式碼> 搬到同一個模組，行為零改變。先記錄目前的輸出，搬完後證明它沒變。`
- 效能：`/poteto-mode <操作> 在 <測試資料> 上要花 <時間>。追蹤它、修掉量測到的原因，給我看前後對照。`

## 設計與計畫

- `/poteto-mode 為 <功能> 做幾個原型選項。截圖或錄影給我比較。`
- `/poteto-mode 我們需要 <功能>。先用 /architect，未決的問題用原型回答。繼續之前讓我審查。`
- `/poteto-mode 先寫一份教學，說明我會怎麼使用 <新套件>。然後用 /teach 教我它為什麼比現在的好。`
- `請 /arena 針對這串討論和我們的做法提供第二意見。`
- `/poteto-mode 把這個設計轉成計畫。拆成小而可驗證的 PR，每個都有自己的驗證步驟。`
- `/poteto-mode 規劃把 <函式庫> 遷移到 <目標>。拆成小而可驗證的 PR。結果必須和原本一模一樣，連 bug 也一樣。`

## 審查與出貨

- `/interrogate 審查整個分支，但要抱持懷疑。先不要改任何東西。除非是真正的 bug 或退步，否則不要挑小毛病。` 也要讀 Dropped 清單。
- `/create-formal-verification-skill 證明 <性質> 在 <模組> 中成立，即使 <步驟> 交錯或重試。` 在那段程式碼合併或重構之後：`/maintain-formal-verification-skill`。
- `/swarm 用每個套件自己的檢查腳本檢查 <資料夾> 底下所有套件。每個套件一個 worker，最後一份報告。`
- `/poteto-mode 開 PR。小而有序的 commit，證據寫在描述裡。`
- `/poteto-mode 看顧這個 PR。讓它全部變綠。` 只要狀態的話：`/poteto-mode 看一下 PR <編號>。還有什麼沒處理的嗎？`
- `/poteto-mode 把這串 PR 合併進去。`

## 離開與回來

- `/poteto-mode 我要去睡了。在一個從 <基底> 開出的新 worktree 中 <目標>。完成的定義是 <檢查>。保留決策紀錄。提交前不用問我。/loop 直到完成。如果過了幾個小時真的卡住了，就停下來寫明原因。`
- `/show-me-your-work 告訴我你昨晚做了什麼。` 先讀它的 Attention 章節。
- `/ketchup` 讓你追上這個聊天自從你上一則訊息之後的進度，並列出每件等你決定的事。
- `/poteto-mode 對這個佇列開全自動駕駛。每一項都是獨立的。`
- `/poteto-mode 用自動駕駛處理這些改動，但不要合併。我自己來合併。`
- `/reflect 把學到的東西記下來，下次別再重蹈覆轍。` 只核准會改變未來決定的修改。
- `/bro` 用白話重講上一則回覆。
