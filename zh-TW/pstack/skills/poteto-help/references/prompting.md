# Word the prompt（構思提示詞）

提示詞說明意圖和完成的檢查方式。步驟由劇本提供，所以幾句白話勝過一份規格書。

> 中文使用者提示：以下說法都可以直接用中文對 agent 說。

## 要放進去的

- 目標。說出哪裡錯了，或使用者想要什麼。
- 完成的檢查。它必須能通過或失敗。「讓它更好」和一段時間長度都不是檢查。
- 要展示的證據。要求真實的指令輸出、流程的影片、儲存的值，或前後對照的數字。
- 使用者已經知道的事。一個症狀、一個重現步驟、一段 log 或一個連結，能幫 agent 省下一次搜尋。
- 真正的限制。「先重現」、「先不要改任何程式碼」、「行為零改變」和「繼續之前讓我審查」，每一句都會改變 agent 的行為。

## 要省略的

- 怎麼做。說要達成什麼，給 agent 空間找到更好的方法。
- 技能或步驟的清單。手寫的順序會漏掉或打亂劇本會保留的步驟。只有要覆寫某個選擇時才點名技能。
- 使用者對原因的理論，要等 agent 複述問題之後再說。說出來的猜測會縮小搜尋範圍。

## 先載入脈絡

- 對於雜亂的回報，在做任何事之前，先請 agent 用自己的話、用白話複述根本問題。誤解會在任何程式碼存在之前浮現。
- 在新的聊天中，先 `/recall` 這個主題之前的工作。舊的聊天握有新 agent 缺少的脈絡。
- 在修改不熟悉的程式碼之前，請 `/how` 說明機制、請 `/why` 說明原因。沒有追蹤過心智模型的 agent，會在第一個看似合理的地方修掉症狀。
- 請 `/teach` 為某個選擇提出論證，例如「說服我它修的是原因而不是症狀」。論證比摘要更容易檢驗。

## 先設計，再計畫

- 永遠不要採用第一個設計。要求幾個選項的原型，UI 的話附截圖或影片，再根據證據挑選。
- 讓原型回答未決的問題。不要對抽象的計畫做對抗式審查，因為審查者會發明永遠不會發生的風險。
- 對於共用的套件或 API，先要求 README 或教學，再倒推回程式碼。文件會成為 agent 用來檢查自己的目標。
- 只有在設計定案後才要求計畫。計畫的每一步都以一次檢查結束。

## 追問可以很短

- 一旦聊天中已經有任務，「做吧」、「繼續」和「一直做到完成」就是完整的提示詞。
- 換主題時以「新任務」開頭。否則模式會把訊息當成下一步。

## 離開之前

- 說「我要去睡了」或「我要離開一下」，讓 agent 不再發問。
- 把完成寫成每次迭代都能跑的檢查，並把那個判定式交給 `/loop`。
- 要求從一個指定的基底開一個新的 worktree。
- 預先回答 agent 會停下來問的事，例如「提交前不用問我」。
- 要求一份之後可以稽核的決策紀錄。
- 給一個出口：「如果過了幾個小時真的卡住了，就停下來寫明原因」。

## 一行就能引導

- 重述目標：「我說的目標是重現。我還沒有要求修正。」
- 點名原則：「apply prove it works。給我看真實的輸出，不是建置 log。」
- 原則名稱有效，是因為 agent 已經讀過那條規則。它的回覆會說出那條規則改變了哪個決定。
