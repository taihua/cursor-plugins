# Create a verification skill（建立驗證技能）

每個認真的專案都需要一個用腳本操作真實 app 並證明行為的方法：啟動它、像使用者一樣操作某個功能，並擷取證據。這個技能會產生一個依 repo 量身打造的專案專用技能（`.cursor/skills/verify-<app>/`）。你寫的產出是給下一個 agent 看的，不是給人看：它會被一個從沒看過這個 app 的 agent，在任務進行到一半時毫無準備地讀到。

## 1. 訪談 repo，而不是使用者

從程式碼庫回答這些問題，只問使用者你觀察不到的事：

- **介面（Surface）：** 使用者實際碰到的是什麼？網頁 UI、CLI/TUI、桌面 app、API、行動 app，還是函式庫？一個 repo 可能有好幾個；挑主要的那個，並記下其他的。
- **執行（Run）：** app 在本機怎麼啟動？優先使用 repo 自己記載的開發指令（package scripts、Makefile、README 快速入門）。記下連接埠、環境變數、種子資料和認證。
- **操作（Drive）：** agent 如何以程式方式與它互動？先找既有的測試框架——Playwright/Cypress 測試、expect 腳本、PTY helper、可以 curl 的端點、除錯連接埠。之後才選通用做法：網頁和 Electron 用瀏覽器/CDP，CLI/TUI 用 tmux/PTY 測試框架，服務用單純的 HTTP。
- **觀察（Observe）：** 能擷取什麼證據？截圖、終端機紀錄、回應內文、log、結束碼、資料庫狀態。
- **隔離（Isolate）：** 兩個實例能並排執行嗎（連接埠、資料資料夾、設定檔）？如果不能，在產生的技能中說明：拒絕同時操作一個共享的實例，勝過毀掉使用者的工作階段。

如果 checkout 原樣無法建置或啟動，在產生之前先修好它（或精確回報）；針對壞掉的基礎寫出來的技能會教錯步驟。當一個無關的缺少資源擋住了啟動（API 從不提供的靜態資料夾、範例設定檔），產生的技能可以建立它，清楚標示為驗證用的鷹架，並在清理時移除。

## 2. 產生技能

寫出 `.cursor/skills/verify-<app>/SKILL.md`，包含 YAML frontmatter（`name: verify-<app>`，以及一個寫明 app、介面和何時使用的 `description`——沒有 frontmatter，技能就不會被註冊），以及下列章節，每一個都要根據訪談實際發現的內容撰寫（不能留任何佔位符）：

- **Launch（啟動）：** 為了驗證而啟動 app 的確切指令，以及如何判斷它已就緒（一行 log、一個提示字元）。啟動必須能從一個空的資料資料夾到達可用狀態，包括任何遷移和種子資料。就緒指的是可用，而不只是某個程序有回應。資料庫的健康檢查可能已經通過，而它的初始化腳本還在跑。包含拆除方式。對於短命的 CLI 或 TUI，沒有需要保持運作的伺服器：啟動代表建置一次執行檔（或安裝相依套件），然後每次操作都在它自己隔離的 PTY 或 tmux 工作階段中開始。
- **Doctor（健康檢查）：** 一個唯讀的檢查，回答「這個實例值得操作嗎？」——程序在運作、版本/建置正確、連接埠屬於我們、認證有效。只要任何東西看起來不對，agent 就先跑這個。
- **Drive（操作）：** 使用這個 repo 真實的選擇器/指令的測試框架做法，而不是範例。偏好穩定的把手（ARIA 標籤、data 屬性、提示字串、路由路徑），而不是座標和 tab 順序。
- **Evidence（證據）：** 為了證明要擷取什麼、放在哪裡。說明證據標準：操作真實的使用者路徑，而不是內部的 setter 或只供測試的端點；擷取動作以及產生的狀態，而不只是最後的畫面；除了看得到的東西，也要驗證副作用（寫入的檔案、插入的資料列、送出的訊息）；只有在正式環境的邊界本來就已隔離外部系統的地方才用 mock。當安全的路徑是試跑（dry-run）或測試模式時，要透過觀察（檔案、網路、git ref）驗證它實際跳過了什麼，而不是相信它的名稱：有些試跑模式仍然會碰網路或打開瀏覽器。
- **Cleanup（清理）：** 如何拆除這次執行建立的實例。永遠不要依程序名稱終止；只終止你啟動的東西。清理會移除實例和暫存狀態，但永遠不移除證據：證明用的成品在拆除後仍然存在，放在技能指定的位置。
- **Helpers（輔助工具）：** 技能附帶的任何腳本都是可執行的，而且它的呼叫方式寫在技能內文中。需要讀者反向工程的 helper 不算 helper。

## 3. 建立功能地圖的種子

建立 `.cursor/skills/verify-<app>/features/README.md`，加上你能找出的每個面向使用者的功能各一個檔案（一開始以前 3～5 個為目標，從路由、指令、選單或文件中找）。依照 [`references/feature-map-example/`](./references/feature-map-example/) 的形狀，有一個 README 索引和每個功能一個檔案。每個檔案從使用者的角度回答：這個功能是什麼、怎麼到達它、如何用測試框架操作它，以及什麼可觀察的最終狀態能證明它正常。四個 H2 標題是 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。如果種子資料缺少某條使用流程需要的前置條件，那條流程就回報失敗，原因寫在該功能的 `Gotchas` 中。永遠不要為了讓它通過而削弱流程。地圖是 repo 中被維護的驗證來源；當地圖列出了其他進入點時，只操作一個方便的進入點的證明是不完整的。

## 4. 交出之前先證明產生的技能

照著它自己的指示端到端跑一次：啟動、doctor、操作**一個**地圖上的功能（一個就夠；地圖的存在就是為了讓之後的執行涵蓋其餘部分）、擷取證據、清理。清理後，確認證據仍然存在於指定的位置——吃掉證明的清理會讓這一步失敗。修正失敗的地方，而且每次失敗的迭代後也要跑產生的清理，讓失敗的嘗試不會留下孤兒程序和連接埠。從沒被執行過的產生技能只是草稿，不是交付物。如果你是在真實目標的替身上證明它（用容器代替全新的虛擬機、用本機堆疊代替遠端堆疊），列出替身做了、但目標不會做的每個設定步驟。在真實目標上的執行涵蓋它們之前，那些步驟都還沒被驗證。

## 5. 提供維護迴圈

告訴使用者，隨著 app 改變，可以用 `/maintain-verification-skill` 讓地圖保持誠實。只有在他們問時才建議執行頻率。
