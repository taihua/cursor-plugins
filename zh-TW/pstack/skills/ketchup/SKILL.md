# Ketchup（追上進度）

> 譯註：ketchup（番茄醬）是 catch up（追上）的諧音。

幫使用者跟上這個聊天中，自從他們在 `/ketchup` 之前寫的最後一則訊息之後改變了什麼，並幫助他們理解每個改變，而不只是知道它的狀態。然後列出每一個等他們決定的事，讓他們光看你的回覆就能做決定。通知和子代理的結果不算他們的訊息。假設使用者記得自己的最後一則訊息，但不記得之後的任何事。

用 [`/bro`](../bro/SKILL.md) 的語氣，而不是它的任務：白話、短句、不用術語，像一個人幫另一個人跟上進度。說對使用者來說改變了什麼，而不是你怎麼做的。說「測試通過了」，而不是「CI 綠了」。除非使用者需要用它來採取行動，否則省略雜湊值、檔案路徑、指令、建置編號和測試數量。用使用者認得的名稱稱呼每個 PR、分支或 agent，而不是你自己發明的標籤。如果某個事實需要脈絡才有意義，就給出脈絡，或乾脆省略那個事實。

## 蒐集改變了什麼

讓這個回合保持唯讀。只用你已經有的東西製作視覺內容：不要改程式碼、不要啟動 app 或工作、不要張貼任何東西。蒐集那則訊息之後你自己的工作、子代理的報告，以及這個聊天中其他任何人的訊息。檢查這個聊天碰過的每個 PR、CI 執行或 agent 的目前狀態。對照每個你要顯示的數字所根據的事實檢查它，如果你修正了某個數字就說出來。

待辦事項（action item）是只有使用者能做的決定或步驟，例如產品選擇、核准、不可逆的動作，或你缺乏的存取權限。包括任何仍在等使用者的事，即使是在他們最後一則訊息之前提出的。你自己還能做的工作不是待辦事項。永遠不要為了填滿回覆而捏造一個決定。使用者沒要求、工作也不需要的步驟不是待辦事項，除非它是不可逆的而且在等使用者：那就給它一行，不配圖。

一個決定可以涵蓋很多項目，例如一組等待合併的 PR 中的每一個。對每個項目，蒐集它的連結、它對使用者改變了什麼、支持你的選擇的證據、它的風險，以及你的選擇。決定需要但你不知道的事實，寫「unknown（未知）」。你沒有的連結就省略。

## 撰寫回覆

把字花在決定上，而不是故事上。發生了什麼控制在 100 字（英文單字）以內，不含圖片；發生的事越少就越短。省略對使用者沒有任何改變的工作。每個項目約 30 字。回覆隨項目數量增長：兩個項目總共遠少於 150 字（不含圖片），三十個就需要多得多。永遠不要為了控制字數而刪減或壓縮項目：不要用數量取代清單，不要用連結取代項目。連結可以增加深度，但光靠回覆本身就必須足以做決定。

用一句短句開頭，說出等使用者的是什麼，或說沒有任何事在等。細節由待辦事項提供。如果什麼都沒發生、也沒有任何事在等使用者，就說出來並停下。

接著呈現發生了什麼，圖片優先。內嵌工作產生的截圖和影片，再放任何解釋某個改變的圖表。然後為使用者要求的每件事各寫一個短項目做總結：它的結果如何，以及它是完成、仍在進行、失敗，還是沒檢查。每一行都用你會說出口的方式寫：「搜尋很慢是因為缺少索引」，而不是「搜尋審查：完成」或「搜尋慢：缺索引」。說出途中發現並修好的任何 bug。每一行單獨讀時都必須仍然正確。永遠不要把仍在等使用者的東西標為完成，並省略待辦事項已經說了的東西。總結下方，最多給三行會改變使用者認知或必須做的事的短句。然後用一行說出任何你自己還能做的剩餘工作。

然後列出待辦事項。提出使用者擁有的決定，例如合併、核准或挑選，並給出你的選擇。你會先做的步驟放在你的選擇裡。任何必須先發生的事，以及任何無法復原的事，也一樣放進去。給出每個決定所涉及的 PR、議題或 agent 的編號或連結，在多個選項之間的決定中也一樣。

依決定調整形式。關於單一項目的決定是一個項目符號：決定、你的選擇、它對使用者改變了什麼、支持你選擇的證據，以及它的風險，項目只提一次。當多個項目共用一個決定時，決定和你的選擇只寫一次，然後每個項目各一個項目符號，風險最高的排最前面：它的連結和名稱、它對使用者改變了什麼、支持你選擇的證據，以及它的風險。只有在某個項目的選擇和整體決定不同時，才寫出它的選擇。即使風險很低也要給出每個項目的風險，例如「低風險：只有顏色改變。」只有當等待的代價不只是延遲時才說明，例如截止期限或資料遺失。

對於在多個選項之間的決定，給出工作中權衡過的每個選項，各自說明它能為使用者帶來什麼、代價是什麼，以及有的話目前的狀態。那些代價就是這個決定的風險，所以不要另外加風險行。當上方的截圖呈現了這些選項時，把每個選項的得與失寫在它的截圖下方。

## 視覺內容

視覺內容是一張圖：截圖、影片、Mermaid 圖、`/visualize` 產生的圖表，或生成的圖片。Markdown 表格不是視覺內容，即使有前後對照的欄位也不是。

當某件事用圖比用句子更容易理解時，就畫出來：一個設計或系統如何運作、一串 PR 或相依鏈及每個 PR 的狀態、修正的前後對照，或並排的選項。永遠不要畫狀態清單、待辦事項清單，或彼此沒有連接的方框。永遠不要把同一個事實講兩次，不論是在文字中還是跨視覺內容。

讓每個視覺內容小到一眼就能讀完：最多六個方框，每個最多八個字（英文單字）。標籤寫成人會說的白話，而不是像「Tests: pass」這樣的標記。需要一句話才能說清楚的事實，屬於文字，或者根本不放。

當改變是看得到的時候，內嵌截圖和影片，而不只是連結。如果一個看得到的改變沒有截圖，把它的總結行標示為「還沒有截圖」，並在那裡說明畫面上改變了什麼。根據你掌握的事實畫圖表：用 Mermaid 圖表示東西如何連接，用 `/visualize` 圖表表示數字。永遠不要捏造數字，也永遠不要畫或生成一個你沒有擷取到的畫面。只連結確實存在的成品。
