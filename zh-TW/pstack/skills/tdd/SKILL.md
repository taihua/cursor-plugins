# TDD Bug Fix（以 TDD 修 bug）

修一個有清楚又便宜的測試路徑的 bug 時，在修改正式程式碼之前，先讓壞掉的行為變成可執行的。目標是一個聚焦的回歸測試：修正前失敗，修正後通過。

不實際的時候不要硬寫測試。如果可用的測試需要大量的測試框架設定、脆弱的 mock、緩慢的端到端基礎設施、只存在於正式環境的狀態、模糊的重現步驟，或大量無關的測試資料變動，就不要新增測試，改用最接近而有用的驗證方式。

## 工作流程

1. **理解 bug。** 找出預期行為、目前行為、受影響的路徑，以及最小的可觀察重現方式。
2. **選擇最窄的可執行檢查。** 優先使用該程式路徑已在使用、最接近的單元、元件、整合或回歸測試。如果沒有明顯可行的測試路徑，不要只為了滿足流程而從零建立一個。
3. **先寫失敗的測試。** 加入能抓到這個 bug 的最小聚焦測試。測試應該編碼預期行為，而不是照抄目前的實作。
4. **修正前先跑新測試。** 確認它因為預期的原因而失敗。如果它通過了，或因為無關的原因失敗，在修改實作前先修正測試或重現方式。
5. **修 bug。** 做出滿足預期行為、同時保留周邊契約的最小正式程式碼改動。
6. **重跑回歸測試。** 確認測試現在通過了。

## 如果失敗測試不實際

改用最接近的可執行回歸檢查：針對性的腳本、手動重現指令、瀏覽器自動化、快照比對、log 斷言，或聚焦的整合檢查。

寧可沒有新測試，也不要壞的測試。壞的測試是指：主要在測 mock、編碼了目前的實作細節、依賴時序或無關的全域狀態、為了一個小修正需要昂貴的基礎設施，或在證明修正後馬上就會被刪掉的測試。

## 護欄

- 不要只為了符合錯誤的實作而修改測試。
- 不要削弱既有的斷言，除非預期行為真的改變了、而且理由很清楚。
- 讓回歸測試聚焦在這個 bug 上。避免大範圍變動測試資料或擴展無關的覆蓋範圍。
- 如果 bug 時有時無，盡可能讓測試具確定性，並記錄被鎖定的訊號。
- 如果 bug 揭露了一整類更廣的失敗，先落地聚焦的回歸路徑，再考慮其他同類的覆蓋。

## 最終回覆

回報證據，而不只是結果：

- 說出「修正前失敗」的測試或可執行檢查，以及它產生的失敗。
- 說出「修正後通過」的測試執行，以及做過的任何周邊驗證。
- 如果無法展示「修正前失敗」的證據，說明原因，並描述改用的最接近回歸檢查。
