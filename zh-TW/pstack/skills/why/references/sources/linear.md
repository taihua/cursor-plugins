# Linear Tickets（Linear 工單）

## 這個來源包含什麼

- 描述功能、bug 及其動機的議題
- 附在議題上的專案文件（常常是 PRD 或規格）
- 父/子議題的關係（較大的計畫 → 具體的工單）
- 議題上的留言（澄清、範圍改變、「我們為什麼要做這個」的理由）
- 標示動機類型的標籤（例如 `compliance`、`customer-request`、`perf`）
- 解釋範圍改變的狀態更新
- 附件和連結的 GitHub PR

Linear 常常是產品/商業脈絡所在之處：「我們做這個是因為客戶 X 要求」或「這是第三季法遵計畫的一部分」這一層。

## 如何搜尋

使用 Linear MCP。

1. **從連結的工單開始。** 如果種子 commit 或 PR 引用了工單 ID（例如 `ENG-1234`、`[BUG-567]`），先用 `get_issue` 取得它們。讀完整個議題，包括留言。
2. **依關鍵字列出相關議題。** 用 `list_issues` 以功能名稱、關鍵符號或商業術語做文字搜尋。試幾種不同的說法。
3. **走過議題樹。** 如果你落在一個子議題上，取得它的父議題。子議題是戰術性的，父議題常常帶有「為什麼」。
4. **讀專案文件。** 如果議題屬於某個專案，用 `get_project` 並查看附加的文件。專案層級的文件最常記錄規格和理由。
5. **檢查標籤和里程碑。** 標籤暗示動機的類別（customer-request、incident-followup、compliance）。里程碑把工作和截止日期連結起來，這常常揭露了動機。

## 這裡的好證據長什麼樣子

- 一個陳述商業問題的議題描述：「客戶 Acme 因為他們的 SOC2 稽核需要 X」
- 一則記錄決定的留言：「我們決定採用做法 B，因為做法 A 需要動到計費服務」
- 一個標題像計畫的父議題：「第三季企業級就緒」或「減少付款失敗」
- 一份附加的 PRD 或規格
- 像 `customer:acme`、`incident-followup`、`compliance`、`perf-regression` 這樣的標籤

## 常見陷阱

- **範圍漂移。** PR 引用的工單可能曾被關閉後又以不同的範圍重新開啟。讀完整個歷史。
- **機械式的模板。** 有些團隊要求「Why」章節，卻用樣板文字填滿。泛泛的文字（「改善使用者體驗」）大概不是真正的答案。
- **過時的工單。** 舊工單常常反映的是後來改變了的計畫版本。檢查日期，並和程式碼的出貨日交叉比對。
- **「以重複關閉」的鏈。** 沿著 duplicate-of 關係追回標準的那張工單。
- **私人工作區的內容。** 如果你無法存取某個議題，把它記為缺口，而不是猜測。

## 要回傳什麼

每張相關的工單：
- 工單 ID 和標題
- 從描述或留言中引用的問題/動機（不要改述。綜合者需要確切的文字來引用）
- 標籤、父議題、專案
- 作者、建立日期、關閉日期
- 有的話，附上工單連結
