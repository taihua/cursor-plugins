# Notion Docs（Notion 文件）

## 這個來源包含什麼

- PRD（產品需求文件）
- 技術規格和 RFC
- 架構決策紀錄（ADR）
- 設計審查的會議紀錄
- 帶有領域脈絡的團隊頁面
- 事件的事後檢討
- 可能解釋防禦性程式碼的維運手冊（runbook）
- 設定優先順序的策略文件

Notion 常常是「為什麼」在變成程式碼之前、以長篇形式存在的地方。一個重要的功能通常會有一份文件。

## 如何搜尋

使用 Notion MCP。

1. **用 `notion-search` 做關鍵字搜尋。** 試試：
   - 功能名稱
   - 目標程式碼中的關鍵符號 / 類別名稱
   - 作者代號（設計文件常常在程式碼落地之前就寫好）
   - 錯誤字串或使用者可見的用語
   - 如果你知道程式碼何時出貨，就用有時間限制的查詢
2. **用 `notion-fetch` 取得候選頁面。** 讀完整的內容，而不是預覽。理由常常埋在文件中段。
3. **追蹤反向連結和子頁面。** 設計文件常常有子頁面記錄考慮過的替代方案、附錄或實作筆記。
4. **檢查相關的資料庫。** `notion-query-data-sources` 和 `notion-query-meeting-notes` 可以浮現討論過這個決定的會議紀錄。
5. **搜尋作者的個人空間。** 如果 PR 作者有個人筆記本（在某些公司很常見），裡面可能有在程式碼之前的探索性思考。

## 這裡的好證據長什麼樣子

- 一份 PRD 的「問題陳述」或「動機」章節，符合目標程式碼的目的
- 一個「考慮過的替代方案」或「被拒絕的做法」章節
- 一份事後檢討，指名目標程式碼是某個特定事件的修正
- 記錄「我們因為 Y 而決定 X」的會議紀錄，而且和 PR 的作者/日期範圍相符
- 一份認真填寫的 ADR 模板（狀態、脈絡、決定、後果）

## 常見陷阱

- **過時的文件。** 規格常常在實作前寫好，之後沒有更新。文件描述的可能是後來改變了的計畫。和實際的 PR 交叉檢查。
- **文件與現實脫節。** 規格可能說「我們會做 X」，但程式碼實際上做的是 Y。標出這個分歧，綜合者會呈現這個矛盾。
- **樣板模板。** 有些組織要求一個「Why」章節，結果被空話填滿。找具體的內容。
- **沒有被連結的文件。** 最相關的文件可能沒有被任何地方連結。廣泛的關鍵字搜尋會有幫助。
- **多份草稿。** 如果一個主題有多份文件，找出定稿或最近更新的那一份。檢查日期。
- **有存取限制的頁面。** 如果你無法存取某個頁面，把它記為缺口。

## 要回傳什麼

每份相關的文件：
- 標題和網址
- 作者和最後更新日期
- 動機文字（逐字引用），附上頁面/章節位置
- 相關的連結頁面（讓綜合者可以引用）
- 文件是定稿還是草稿
