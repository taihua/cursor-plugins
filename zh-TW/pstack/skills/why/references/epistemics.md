# Epistemics（認識論：如何判斷信心程度）

當證據是歷史性的、零碎的、有時互相矛盾時，如何推理信心程度，以及如何告訴使用者而不把它壓扁成虛假的確定性。程式碼顯示它做什麼，而不是*它為什麼存在*。原因存在於 commit、PR、工單、文件和對話中，全都不完整、有偏差，有時甚至不存在。假裝不是這樣，只會產生聽起來很有自信、卻會誤導使用者的猜測。

## 信心等級

輸出中的每個主張都必須屬於一個等級。等級決定它放在哪個章節、用什麼措辭。

### 1. Direct（直接）

一個明確的文字引用回答了問題：某位作者實際*寫下*了原因，而不是「程式碼做 X，所以作者一定想要 X」。例如，PR 描述「這修正了有超過 1000 個項目的使用者無法分頁的 bug」、工單「我們加這個是因為客戶 Acme 在他們的安全審查中要求」、程式碼註解「// 限制在 100，因為上游 API 會拒絕更大的值」、設計文件「我們選擇方案 A 而不是方案 B，因為我們需要跨重啟的持久性」，或作者的聊天訊息「改用這個做法，因為舊的在測試中不穩定」。

措辭：有自信、現在式、附出處。「這之所以存在，是因為 X。」

### 2. Supported（有支持）

多項間接證據收斂到同一個結論。沒有單一來源明確說出它，但跨來源的模式讓它很可能成立。例如，PR 標題說「改善效能」、工單被標為「perf」、周圍的 commit 全都碰同一條熱路徑。或者，隨改動新增的好幾個測試都在測非常大的輸入。或者，作者同一週的其他 PR 都提到同一個事件。

措辭：有自信但明顯是推導出來的，引用每一項。「證據強烈指向 X：[具體的各項證據]。」

### 3. Inferred（推論）

對脈絡的合理解讀，但沒有任何東西明確支持它。它是*你的詮釋*，不是紀錄中的事實。例如，PR 沒說原因，但錯誤當時正在正式環境發生（依事件頻道的時間點），而且修正很倉促（當天就合併），所以它很可能是個緊急修正。或者，函式名稱暗示有重試邏輯，而它的重試次數 3 和程式碼庫其他地方團隊的 3 次重試慣例一致。

措辭：有保留，並明確寫出推論鏈。「根據 A 和 B，C 似乎很可能，因為 D。」

### 4. Speculative（推測）

建立在薄弱證據上的合理假設，而其他解釋也同樣說得通。值得呈現，因為使用者可能知道哪個是對的，但要標示為猜測。例如：「這可能是為了繞過某個已經修好的瀏覽器 bug，但我們沒有找到當時的證據」，或「這個門檻值有可能是為了符合某個 SLA 承諾而選的，但沒有任何 SLA 文件提到它。」

措辭：「一種可能是 X，但我們沒有直接證據。」通常放在「競爭的假設」中，和其他可能性並列。

### 5. Unknown（未知）

你找了，但找不出來。這是有效而且重要的結果。把它記錄下來。

措辭：「我們搜尋了 X、Y 和 Z，沒有找到任何說明原因的證據。」具體說明你搜尋了*什麼*。「我們找不出來」不如「我們用關鍵字 A 和 B 搜尋了工單追蹤系統、掃過 2023 年以來碰過這個檔案的 6 個 PR，並在 repo 中 grep 符合這個門檻值的字串常數。沒有任何一項浮現出理由。」有用。

## 措辭指南

**表達信心的詞**暗示有 Direct 或 Supported 的證據，必須緊接著附上出處。永遠不要用在推論上：「因為」、「原因是」、「被設計來」（宣稱作者的意圖）、「修正了」/「處理了」/「解決了」（宣稱改動達成了目標）、「團隊決定」（宣稱發生過團體決策）。

**保留語氣**代表詮釋，而不是報告。在「我們可以合理推論什麼」中大方使用它們：「看起來」、「似乎」、「很可能」、「暗示」、「與……一致」、「一種解讀是」、「說得通的是」、「可能曾經」、「證據指向」。

**要避免的詞：**

- 「顯然」。如果很顯然，使用者就不會問了
- 「明顯地」。幾乎總是出現在一個並不明顯的主張之前
- 「當然」。同上
- 「只是」（例如「這只是為了效能的 X」）。帶有輕視，而且通常掩蓋了不確定性
- 「我認為」/「我相信」。你是在綜合證據，不是在給個人意見。改用「證據顯示」。

## 避免合理化

今天「說得通」的程式碼，可能是基於已經不再適用的理由寫的，或是在當時就錯了。不要把一個乾淨的理由硬套到混亂的歷史上。不要假設作者做了「對」的事，再倒推去替它辯護。不要假設一個一致的模式是刻意的，它可能只是複製貼上。不要把「沒有證據」變成「不存在的證據」（「沒有人提到安全疑慮，所以那一定不是個疑慮」）。

## 奉承陷阱

使用者常常在問題中夾帶一個假設：「我們為什麼這樣做，我猜是為了效能？」不要直接確認它。這個猜測是調查的起點，不是要被背書的結論。把它當作眾多候選之一，獨立檢查證據。如果證據支持它，附出處說出來。如果不支持，也說出來，並呈現證據*真正*支持的東西。

## 當證據互相矛盾時

在輸出中附出處呈現兩個來源。不要挑那個能讓故事更整齊的。例如，工單說「我們需要這個來符合客戶 X 的法遵要求」，而 PR 說「清理這個區域的技術債」。兩者可能都是真的（工單促成了這項工作，PR 呈現的是作者的框架），也可能其中一個是錯的。讓使用者做判斷。

## 當證據缺失時

誠實的「我們不知道」是最有價值的輸出之一。使用者會知道答案不在顯而易見的地方、他們需要去問人（原作者、產品負責人、團隊主管），或者他們可以決定這個問題不值得再追下去。沒有標出缺口、反而用一個有自信的猜測填補它，會主動傷害使用者，因為他們會依那個猜測行動。具體說出每個缺口：問題、搜尋過的來源、在每個來源中搜尋了什麼，以及找到了什麼（什麼都沒有，或只有不太相關的材料）。

## 定稿之前

在綜合者交出輸出之前，它要檢查「我們發現了什麼」和「我們可以合理推論什麼」中的每個主張。每個主張都有出處，否則就移到「推論」或「假設」。它的措辭符合它的等級。它沒有把程式碼當作它自身意圖的證據（如果有，移除或重新分類）。輸出有一個「我們不知道什麼」章節。如果完全沒有提到任何缺口，那就很可疑：要嘛證據異常完整，要嘛有什麼東西被掃到地毯下了。
