# Automate me（把我自動化）

一個引導式流程，把使用者的工作慣例變成 agent 會遵循的技能。產出是一個為他們量身打造的 `-mode` 技能（例如 `jay-mode`、`priya-mode`）。

這個技能統籌另外三個：一個內嵌的挖掘步驟（見第 1 步）、Cursor 內建的 `create-skill`（撰寫），以及 **unslop** 技能（文字紀律）。它負責安排它們的順序，而不是取代它們。

## 流程

### 0. 檢查是否已有技能

遞迴尋找符合使用者代號的 `.cursor/skills/**/*-mode/SKILL.md` 和 `~/.cursor/skills/*-mode/SKILL.md`。mode 技能可能放在個人分類資料夾中（`.cursor/skills/<handle>/`），而不只是在頂層。如果已經有一個，用 `AskQuestion` 確認意圖（除非他們已經說了「更新我的技能」之類的話）：

- 更新既有的技能（重複執行時的預設）
- 從頭開始（很少見，做之前先問原因）

更新模式會改變流程的其餘部分：
- 第 1 步只挖掘技能上次修改之後的紀錄（`git log -1 --format=%cI <path>`）。
- 第 2 步問的是什麼改變了或缺少了什麼，而不是從零開始要記錄什麼。
- 第 4 步直接修改既有的檔案。保留使用者沒有推翻的章節。修訂有新證據的章節。只為真正新的規則新增章節。

### 1. 挖掘他們的紀錄

分派之前，先找到目前工作區的對話紀錄。系統提示詞會給出工作區的 `agent-transcripts/` 目錄，只用那個路徑。不要對 `~/.cursor/projects/*/` 做 glob，那會跨越工作區邊界，讀到無關專案的私人聊天。

在那個範圍內調查最近的 agent 對話，找出反覆出現的模式。在紀錄的不同區段跑多個平行子代理（例如最近 2～4 週，分成 3 段，讓每段都有足夠的材料）。依 **poteto-mode** 技能的「子代理」章節，為每個子代理選擇工作需要的推理等級與快速或標準速度。每個區段的挖掘子代理從父代理提供的工作區範圍路徑讀取對話紀錄，尋找下列訊號，並回傳一份簡短的結構化清單，列出它看到的模式和證據指標。預設值得追查的訊號：

- 回覆偏好（長度、語氣、格式、「講白話一點」之類的糾正）
- 委派習慣（子代理、模型、專門的工作流程、平行化）
- 驗證姿態（「完成」代表什麼、單元測試 vs 實際重現、審查者）
- 程式碼和文字紀律（風格、引用的原則、lint/格式化工具）
- 流程慣例（worktree、commit、PR、審查/合併工具）
- 後設偏好（在任務中途修正技能、提議新技能）

在提升某個訊號之前，跨區段交叉比對。在 2 個以上區段看到的模式信心高。單獨出現的訊號很弱，通常會被拿掉。

### 2. 直接問使用者

挖掘會漏掉還沒出現過的意圖。使用 `AskQuestion` 工具（結構化多選題），而不是要使用者從零開始打字。

形式：一兩個問題，每個 4～6 個選項，分類型的問題用 `allow_multiple: true`。從廣泛的問題開始（「哪些方面最重要？」），然後針對選中的方面追問具體選項。結構化的回合之後，用一個自由回答的聊天問題抓住選項漏掉的東西。

不要一次丟出 20 個問題。

### 3. 歸納發現

把合併的訊號分組成章節。常見的章節（只用適用的）：

- **回覆風格**：長度、語氣、格式。
- **自主程度**：不用問就做多少、MCP 工具的使用。
- **先理解**：在界定範圍或調查一個改動時要用哪些技能。
- **子代理**：預設值、平行化、模型與任務的對應、專門的工作流程。
- **文字 / 程式碼紀律**：原則、lint 工具、風格指南。
- **審查與驗證**：重現的姿態、驗證技能、實際測試工具。
- **流程**：git worktree、commit、PR、審查/合併工具。
- **技能**：撰寫技能的習慣、先修技能、提議新技能。

**poteto-mode** 技能展示了形狀。讀它來了解細緻程度，但不要複製它的內容。使用者的規則和 poteto-mode 的不一樣。

### 4. 起草技能

使用 Cursor 內建的 `create-skill` 技能撰寫技能。位置：

- 路徑：保留既有 mode 技能的分類。新的 mode 的話，如果 repo 已經為那個代號建立了個人分類，就用 `.cursor/skills/<handle>/<handle>-mode/SKILL.md`。否則預設為專案中的 `.cursor/skills/<handle>-mode/SKILL.md`（如果使用者偏好個人技能，就用 `~/.cursor/skills/<handle>-mode/`）。
- 代號：使用者的名字或他們選擇的識別名稱。
- Frontmatter `description`：以他們的名字 + `/<handle>-mode` + 「用他們的風格工作」作為觸發條件，而不是像「寫程式」或「審查 PR」這樣的通用關鍵字。
- Frontmatter 格式：遵循 `create-skill` 的 YAML 規則。讓 `description` 保持為一個 YAML 純量。當標點或換行需要時，加上引號，或用 `description: >-` 搭配縮排的續行。
- Frontmatter 預設 `disable-model-invocation: true`。只有在使用者明確希望他們的模式在每一輪都套用時才取消。

### 5. 反覆修改文字

對每一行套用 **unslop** 技能和 `create-skill` 的寫作指引。

把草稿給使用者看並接受回饋。預期要多次迭代。毫不留情地刪。mode 技能不是使用手冊。

### 6. 落地

在從 main 分出的 worktree 中工作。提交並開 PR。不要直接推送到 main。

## 護欄

- **不要對單一對話過度擬合。** 說過一次、另一次又被推翻的偏好是雜訊。要有多次出現才把它寫成規則。
- **不要耍聰明。** 重述其他技能的內容、發明比喻，或為 agent 讀者寫「詩意」的文字，只有成本沒有好處。保持可操作。
- **引用，而不是內嵌。** 使用者依賴的其他技能應該以路徑引用出現，而不是貼上摘錄。他們在別處維護的任何原則文件也一樣。
- **章節保持最少。** 只有當使用者在那裡有具體、非預設的規則時才加一個章節。「清楚溝通」不是一個章節。「短段落。比較選項時用表格。只有項目真的平行時才用項目符號。」才是。
- **命名慣例要通用。** 在祈使句中用「使用者」或「人類」，而不是作者的名字。
- **不要硬湊對稱。** 如果使用者沒有值得寫下的流程規則，就整個跳過「流程」章節。

## 評估

`-mode` 技能是主觀的產出。`create-skill` 式的測試/迭代基準迴圈在這裡沒什麼用。和使用者一起憑感覺檢查：讀起來像他們嗎？有漏掉什麼嗎？然後出貨。

只有在實際使用中發現技能的觸發準確度有問題時，才跑描述最佳化迴圈。

## 何時不要用

- 使用者想要一個針對特定任務的技能（而不是工作慣例）：單獨用 `create-skill`，不需要挖掘。
- 使用者想記錄一個很窄的工作流程（例如「我怎麼寫 commit 訊息」）。那是一般技能，不是 mode 技能。
