# Show me your work（給我看你的過程）

保持一份標準的 log。

## 格式

單一個 TSV 檔案，每個決策一列。儲存格保持單行。證據是一個指標，不是一段文字。

複製 `references/decision-log-template.tsv`（標題列）來開始一份乾淨的 log。欄位：

- **ts。** ISO8601 時間戳記。
- **phase。** 階段或工作流。
- **decision。** 選擇或做了什麼，一行。
- **why。** 用白話說明理由。如果是某條原則推動的，就直接說出來，不要用術語標籤。
- **evidence。** 證明它的連結或路徑：commit SHA、PR 編號、`file:line`，或成品、trace 或截圖的路徑。永遠不要是一段文字。
- **result。** 結果或判定式的狀態：`tests green`、`reverted`、`pixel-diff 0`、`INCONCLUSIVE`、`open`。

一個範例，用白話寫，讓審查者一眼就能讀懂（以下為中文意譯）。

```
ts	phase	decision	why	evidence	result
2026-05-24T09:02:00Z	frame	先盤點工作量，大約 100 個元件、約 75 小時	想在開始長時間執行前先知道規模	commit 3a9f1c2	找到 5 件開始前要先處理的事
2026-05-24T09:40:00Z	harness	在改任何東西之前先截下舊版的畫面	這樣就能新舊比較，抓到任何視覺變化	scripts/snapshot.sh, baseline/	存了 120 張參考截圖
2026-05-24T11:15:00Z	widget	把 widget 的樣式搬過去，外觀不變	讓改動保持小、結果保持一致	commit 7c21e0a, pixel-diff 0	看起來一模一樣，測試通過
2026-05-24T12:30:00Z	widget	丟掉一個幫手的成果，因為它的截圖是空白的	檢查了真實的檔案，而不是相信它的摘要	worktree reset	已還原，並收緊了下次的指示
```

## 記錄一列

每一筆都用你會告訴隊友你做了什麼的方式寫。白話、具體的動作，不要 AI 腔或抽象術語（**unslop** 技能也適用於 log 文字）。

使用 helper `scripts/log.sh <logfile> <phase> <decision> <why> <evidence> <result>`。它會蓋上 `ts`、在第一次使用時寫入標題列、移除多餘的 tab/換行，並在任何以 `=`、`+`、`-` 或 `@` 開頭的儲存格前面加上一個單引號。直接用 `printf` 附加一列也可以，但如果儲存格內容來自產生的或使用者提供的文字，要注意同樣的那些字元。

記錄決策點和檢查點，而不是每個動作：選擇了一條分岔、完成了一個單元及其驗證結果、一次轉向或還原及其觸發原因、浮現的阻礙、修好的關卡。迴圈執行的話，每次迭代一列。跳過瑣碎和不言自明的事。

一次執行（run）是一段 agent 對話，包括它之後的回合以及對它的任何摘要。一次接手、一個替代 agent 或一個新聊天，都會開始一次新的執行。當一次執行要在已經有資料列的 log 中新增內容時，它的第一列的 phase 是 `start`；在另一次執行的 `start` 列之後，它的第一列也是 `start`。所以，一次在之後的回合回到 log 的執行，要先讀 log 的最後幾列，看看是否有另一次執行在這之後寫入過。`start` 列要寫明在它之前、不是這次執行寫的那些資料列的 `ts` 範圍，它的 evidence 要寫明這次執行，例如它的 agent id。`start` 這個 phase 不做其他用途。

## 它放在哪裡

預設情況下，log 是一個工作用的成品，不提交。把它放在工作資料夾中的 `decisions.tsv`，或在同時進行好幾項工作時放在 `.audit/<task-slug>.tsv`，並把它排除在 git 之外。

只有當工作夠有野心、審查者需要這份紀錄才能信任結果時，才提交它。

## 規則

- 只能附加。錯誤的決定用新的一列取代它。永遠不要編輯或刪除歷史。
- 偏好由已提交的腳本產生的證據，而不是手工的一次性產物（**encode-lessons-in-structure** 原則技能）。

## 對照對話紀錄稽核 log

在執行結束、交回之前，檢查 log 是否說了實話。讀這次執行在目前工作區 `agent-transcripts/` 目錄下的對話紀錄（系統提示詞會給出路徑）。不要對 `~/.cursor/projects/*/` 做 glob，那會讀到無關的私人聊天。把這次執行的資料列和實際發生的事對照。這次執行的每一段資料列，從這次執行的某個 `start` 列開始（如果是這次執行建立了 log，就從第一列開始），到另一次執行的下一個 `start` 列結束：

- 確認每一列都對應到一個真實的決策或動作。
- 確認每一列的證據都能解析，並顯示了那一列所宣稱的內容。
- 一個影響了工作、卻沒有被記錄的分岔、轉向或被放棄的做法，就是一個缺口。把它加進去。

修正 log，而不是修正故事。稽核永遠不會編輯或移除任何一列，即使是捏造的。當某一列既沒有記錄真實的決策也沒有記錄真實的動作，或它的主張或證據是錯的，就加一列取代它，寫出實際發生了什麼，並附上能解析的指標。這次稽核不檢查這次執行的段落以外的資料列。如果這次執行自己的工作顯示其中某一列是錯的，就像處理任何錯誤的決定一樣取代它。

## 跨模型審查紀錄

交回之前，派出一個與做這份工作的模型**不同家族**的子代理。自我審查不能取代它。子代理讀稽核紀錄和這次執行的對話紀錄，然後標出使用者應該注意的地方。不是重做工作，而是掃描次佳或有風險的地方。依 **poteto-mode** 技能的「子代理」章節，為每個子代理選擇工作需要的推理等級與快速或標準速度。

- 證據薄弱或缺少證據的決策。
- 被跳過、或在對話紀錄中沒有證據就宣稱完成的驗證步驟。
- 事後看來有風險的選擇（過早、範圍蔓延、掩蓋症狀）。
- 使用者隨便瀏覽時會漏掉的缺口。

每一次產生了紀錄的執行，回覆都以一個「Attention（注意）」章節結尾。第一行單獨寫出審查者的模型（`reviewed by <model>`），然後列出每個標記，指向特定的資料列或時刻。「No flags（沒有標記）」是有效的值。模型名稱則不能省略。

## 審查紀錄

從上往下讀，跟著證據指標走，抽查。GitHub 會把提交的 TSV 渲染成表格。`column -s$'\t' -t decisions.tsv` 可以在終端機中把它渲染出來。

## 與這個技能組合

其他技能把它們的稽核紀錄導向這裡，而不是自己發明一個。用名稱引用它，讓它負責格式。不要重述欄位。
