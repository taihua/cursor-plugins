# Explain the Number（解釋這個數字）

- **執行前先寫下決策。** 說出什麼樣的結果會改變一個決定，以及雜訊的下限。當每次執行之間的差異比效果本身還大時，就停下。
- **問「為什麼不是兩倍？」** 說出限制結果的資源或程式路徑，例如某個核心、某個鎖、磁碟、網路，或負載產生器本身。從效能分析或執行期間擷取的系統計數器取得它，再對應回原始碼。讀程式碼得出的猜測不算瓶頸。如果你說不出為什麼這個數字沒有好兩倍，你就不知道自己量到了什麼。
- **列出這個數字還可能在量什麼，並用證據逐一排除。** 常見的嫌疑包括：錯誤、被跳過或被快取的工作、從未執行的程式碼、沒有調校的一方（保持預設設定的那一邊）、雜訊，以及一個小到在端到端來看無關緊要的部分。
- **讓證據跟著數字走。** 把執行次數、差異範圍和瓶頸放在筆記或連結的成品中。

效能數字的話，用 [benchmark-checklist](../benchmark-checklist/SKILL.md) 技能跑完整流程。eval 結果的話，對每次試驗問同樣的問題：每次執行都有完成任務嗎？差距在不同試驗和不同模型之間都成立嗎？這個情境重要嗎？

你跳過這條原則的徵兆是：開始執行時沒有寫下「會改變決定的結果」；數字背後的證據沒有執行次數、沒有差異範圍或沒有指明的瓶頸；或者省下的時間比被改動的那部分原本花的時間還多。

和 [Prove It Works](../principle-prove-it-works/SKILL.md) 不同，後者是檢查一個輸出是否真實。
