# Blast radius（影響範圍）

在出貨之前，找出一個改動在別處弄壞了什麼。用於「X 的影響範圍」、「這可能弄壞什麼」，或審查一個你還不放心的小 diff。

是 `how` 和 `why` 的夥伴。`how` 告訴你程式碼做什麼，`why` 告訴你它為什麼長這樣，blast radius 告訴你它在別處弄壞了什麼。

列出呼叫者不是這份工作的重點，agent 一秒就能 grep 出來。重點是 grep 看不到的破壞。

## 不要相信你自己寫的說明

一份聽起來很對的影響範圍說明毫無價值。不管它是真是假，讀起來都很有說服力。所以不要交回說明。找出整件事所依賴的一兩個事實，用執行程式碼來證明它們。

### 你有多確定

對於改動的安全性所依賴的每個事實，在成本低的範圍內，把它推到這份清單越下面越好，並說明它停在哪裡。

1. 你說了而已。單獨來看毫無價值。
2. 你指出了那一行。一個真實的 `file:line`，或函式庫本身的原始碼。
3. 你證明了壞的情況不可能發生。你一步一步走過失敗路徑，它到不了。
4. 你執行了它。一個呼叫真實程式碼的腳本或測試，如果你錯了它就會大聲失敗。
5. 你在執行中的 app 裡重現了它。

第 4 步通常是一個小腳本，它 import app 出貨時用的同一個函式庫，並呼叫你擔心的那個確切函式。

## 步驟

1. 讀這個改動。diff、它新增、修改和刪除的符號，以及它現在的行為有什麼不同，包括 diff 沒有寫明的部分。用 `why` 的第 2 步把 PR 和 commit 拉出來。
2. 找出「它之所以安全」的那個事實。大多數看起來有風險的改動，都是因為某一個事實而安全，例如「這個呼叫只會丟掉已經失效的快取項目，其他什麼都不做」。找出那個事實。如果它成立，大多數有風險的情況會一次被排除。把時間花在這裡，而不是一長串的「也許」。
3. 去看 grep 看不到的地方。讀你呼叫的函式庫的原始碼，檢查它被釘住的版本和任何本地 patch。搞清楚東西什麼時候執行：microtask、卸載與拆除、Solid 與 React 的差異。追蹤符號搜尋漏掉的東西：API 回傳的 JSON、資料庫欄位、線路格式、讀同一組位元組的另一種語言、feature flag、往下游三跳的程式碼。
4. 誠實面對每個風險。給它一個真實的發生機率，以及發生時真實的代價。保留你確認的風險。把你檢查過並排除的另外列出來。規則和 `why` 一樣：引用真實的 `file:line`，搜尋不到東西也是一個答案，永遠不要捏造呼叫者或 API。
5. 證明那個關鍵事實。寫一個執行真實程式碼的腳本或測試，執行它，貼上發生了什麼。
6. 對於大型或範圍廣的改動，以 `arena` 執行。問不只一個模型同樣的問題，合併答案。不同的模型會抓到不同的真實 bug。

## 要交回什麼

- **它做什麼。** 改了什麼，包括不明顯的部分。
- **它之所以安全的那個事實。** 說明它、說它推到了第幾步，並展示證明。如果無法證明，寫 unproven（未證明）。
- **風險。** 每個風險都寫明它如何造成破壞、`file:line`、可能性和嚴重程度，以及如何檢查。重要的風險要貼上證明。
- **已排除。** 你檢查過什麼，以及為什麼沒問題。
- **合併之前。** 能抓到真正 bug 的最便宜測試或重現方式，包括你寫的腳本。

用 `unslop` 撰寫，引用真實的程式碼，並在發布到任何公開地方之前移除私人的內容。

**回覆：** 上述的說明，其中那個安全事實要嘛已被證明，要嘛標示為未證明。
