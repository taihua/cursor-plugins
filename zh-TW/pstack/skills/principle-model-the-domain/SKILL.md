# Model the Domain（為領域建模）

把真實的領域編碼在一個資料結構中，而不是散落在各處的條件判斷裡。一個符合領域的結構會讓不合法的狀態無法被表示，並刪掉分支。在撰寫時就選擇它很便宜；之後才補救，看起來就像一次重構，而且會被延後。

考慮使用：

- 用狀態機取代散落的布林值、階段或生命週期檢查。
- 用型別化模型取代鬆散的參數或重複的結構假設。
- 用 map、註冊表、查找表或 discriminated union 取代散布在各檔案中的分支。
- 用 reducer 或指令/事件模型取代臨時的狀態修改。
- 圍繞一塊領域知識組織的模組，而不是依照像「載入、驗證、轉換、儲存」這樣的順序。執行順序不等於所有權。
- 一個能聚集重複行為、所有權或不變條件的小模組邊界。
- 當存取模式需要時，使用佇列、快取、索引、圖、樹或正規化的集合。
- 任何其他合適的結構。當沒有合適的時，先搞清楚程式碼絕對不能允許什麼、資料會如何被讀取，再找出恰好能編碼這些的結構。

不要硬套抽象。如果目前的形狀已經清楚、局部、而且不太可能擴張，就偏好平凡的程式碼。對於只增加間接層、卻沒有移除分支、重複規則、不合法狀態或生命週期風險的抽象，要抱持懷疑。

你跳過這條原則的徵兆是：新功能讓既有的 if/else 鏈多長出一個分支，或出現第二個必須和第一個保持同步的布林值。依時間拆解是另一個徵兆：以階段命名的模組會在各個步驟中重複同樣的領域規則。
