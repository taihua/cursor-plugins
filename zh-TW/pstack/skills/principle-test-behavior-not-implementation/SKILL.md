# Test Behavior, Not Implementation（測行為，不測實作）

測試是對「程式碼為它的使用者做了什麼」的主張。使用者可能是呼叫者、終端使用者或另一個服務。行為是那些使用者透過他們使用的介面所能觀察到的東西，包括回傳值、錯誤、他們能讀回來的狀態，以及對程式碼以外系統的影響，例如送出的請求、寫入的資料列或發出的訊息。實作則是他們觀察不到的東西：私有的 helper、內部呼叫順序、中間資料，以及是哪個內部協作者完成了工作。

用兩個想像中的修改來評判每個測試：

- **弄壞行為。** 讓程式碼回傳錯誤的值、跳過一個效果，或讓效果發生兩次。如果測試仍然通過，它就什麼也沒證明。常見原因有：斷言比契約寬鬆、預期值是由受測程式碼算出來的、重述了一個常數或提示詞字串卻從沒執行讀取它的程式碼，以及斷言的是測試自己建構的資料。
- **改變內部。** 保持每個可觀察的結果不變，重組底下的程式碼。如果測試現在失敗了，它就被釘死在實作上。每次重構都要重寫它，而它仍然抓不到任何 bug。

保留能抓到第一種修改、又能撐過第二種修改的測試。其餘的重寫或刪掉。要寫出兩者兼具的測試，就用一個具體的輸入，透過使用者的介面驅動程式碼。從需求推導預期值，而不是從執行程式碼的結果推導。斷言契約所承諾的東西，不多也不少。

決定權在契約，而不是斷言的形式。當承諾是「空的購物車永遠不會扣款」時，斷言付款客戶端沒有被呼叫就是行為。再搭配一個確實會扣款的案例，讓測試證明它看得到呼叫。被 mock 的外部服務收到的酬載是行為，因為那個服務觀察得到它。對內部 helper 的呼叫是實作，因為沒有使用者看得到它。當沒有紀錄符合時，空清單就是確切的答案；但當測試只需要「有某個結果」時，它就是一個空洞的檢查。確切的錯誤訊息釘死的是沒有呼叫者會讀的措辭；呼叫者據以分支的錯誤型別才是契約。

測試也可以釘住一個不變條件而不是一次呼叫，例如某個鍵必須同時存在於兩張表中，或一個編譯期的型別檢查。那個不變條件就是行為。
