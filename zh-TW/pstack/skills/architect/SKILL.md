# Architect（架構師）

用 `not implemented` 的函式本體和虛擬碼，草擬型別、函式簽名、類別形狀和模組邊界。綜合多個模型的觀點，然後依選定的草稿填入程式碼。

## 開始

開始前，開一份待辦清單，每個階段一項。

1. 打基礎
2. 草擬
3. 取得共識
4. 實作
5. 砍掉重練

## Phase A：讓問題有依據

為新程式碼碰到的每個系統建立真正的心智模型。對相關的子系統執行 **how** 技能。說出一個檔名不算打基礎。產出 `how` 規定的架構說明。如果設計重新定義了所有權或分層，也對既有的形狀執行 **why** 技能，讓理由成為一個限制條件，而不是猜測。

只有在工作真的是全新的、沒有周邊系統需要整合時，才跳過 Phase A。

## Phase B：草擬

用設計草稿任務和 Phase A 的基礎成品執行 **arena** 技能。把 `references/runner-prompt.md` 作為每個執行者的提示詞。

從 `pstack-models.mdc` 規則中的 `architect runners` 設定行取得執行者，取代 `arena runners` 設定行。如果規則或該行不存在，使用 `claude-opus-5-5-xhigh` 和 `grok-4.7-xhigh-fast`。別名和被拒絕的項目依 **arena** 技能 Phase A 中的執行者規則處理。

設計兩次。在綜合之前，至少要有兩個結構上不同的候選，即使第一個看起來就夠了。這就是 **exhaust-the-design-space** 原則技能的具體化。要的是整體形狀的替代方案，而不是在同一個形狀裡做局部修正。

在綜合之前，用 [`references/design-red-flags.md`](./references/design-red-flags.md) 篩檢每個候選。假設下一個貢獻者是一個 agent：它只看得到自己打開的檔案、會複製最近的範例、會走能編譯通過的最短路徑。偏好那種「從一個檔案看起來對的改動，對整個 repo 也是對的」的設計。

在介面深度上比較可行的候選。偏好在更小、更簡單的公開介面後面隱藏更多複雜度的設計。一個豐富的介面可以透過集中能力、而不是把它散布到各層，讓呼叫鏈保持簡短。

Arena 會回傳一個綜合後的設計套件。它的綜合決策會填入理由文件的「Synthesis decision」章節。

## Phase C：取得共識（選擇性）

預設：用綜合後的設計直接進入實作。沒有人類檢查點。

當呼叫者明確要求時，才加入檢查點：「/architect with checkpoint」、「實作前先停下來給我看」或類似的說法。這時呈現綜合後的設計，並暫停等待簽核。

不論哪種情況，綜合結果都可以作為自己的 commit 出貨，也就是 **foundational-thinking** 原則技能的「骨架優先」模式。依 **outcome-oriented-execution** 原則技能，在填入過程中有計畫、有範圍的損壞是可以的。如果想在實作前對設計施加對抗性壓力，就對綜合後的草稿執行 **interrogate** 技能。

如果人類對形狀提出反對（在檢查點或事後），把它當作 Phase A 的證據。重新打基礎，並在寫更多程式碼之前重跑 Phase B。

## Phase D：依草稿實作

把 `not implemented` 的本體換成程式碼，把虛擬碼換成邏輯。綜合後的草稿就是契約。偏離它是需要呈報的訊號，而不是默默吸收的摩擦。如果某個函式需要一個草稿沒預料到的參數，就問：是草稿錯了、需求被漏掉了，還是實作做過頭了？

## Phase E：架構錯了就砍掉重練

如果實作不斷產生草稿無法吸收的摩擦，就把草稿丟掉。依 **redesign-from-first-principles** 和 **fix-root-causes** 原則技能，不要在錯誤的設計上硬加修正。

訊號是一種**模式**，而不是單一事件。徵兆：

- 同一種形狀的繞路寫法在不相關的程式碼中反覆出現。
- 多個不相關的邊界情況都需要特例分支。
- 型別需要逃生口（`any`、強制轉型、實際上總是有設定的可選欄位）才能編譯。
- 草稿說狀態不共享，卻出現「我們需要一個鎖」的反射動作。
- 呼叫者必須知道抽象的內部規則才能使用它。
- 在實作中出現兩個以上同樣形狀、彼此獨立的 Phase D 偏離。

運用判斷。幾個邊界情況不足以判一個架構死刑。有些問題本來就很複雜。資料中的複雜不等於設計中的複雜。

砍掉重練時：

1. 對已經建好的東西重新執行 **how** 技能。
2. 依 redesign-from-first-principles，把新的限制當作從第一天就存在的假設來重新設計。
3. 依 **subtract-before-you-add** 原則技能，先減再加。新的草稿在長大之前，應該比舊的更小。
4. 回到 Phase B，重跑 arena。

## 輸出

先寫呼叫者的用法，再從它推導出型別草稿。小改動的話，一個檔案放新的型別和簽名。較大的工作則是模組地圖加上型別定義。理由文件一起交付，依 `references/rationale-template.md` 的格式，包括用法草稿和綜合決策。
