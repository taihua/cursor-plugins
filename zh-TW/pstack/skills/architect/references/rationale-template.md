# Rationale template（理由文件模板）

隨著型別草稿一起交付的文字。一頁。標題用句首大寫，不要樣板文字。把斜體的說明換成實際內容。

## Problem（問題）

*一段。我們想做什麼，以及既有系統或限制中有什麼讓這個形狀不那麼顯而易見。如果 [Phase A](../SKILL.md) 浮現了設計必須遵守的限制（需要互通的既有型別、不能弄壞的呼叫者、跨越我們邊界的不變條件），在這裡寫出來，讓讀者看到和你一樣的限制。*

## Usage（使用方式，呼叫者的視角）

*在型別草稿之前先寫這個。展示使用者會讀的 README 或快速入門，加上兩三個在他們自己程式碼中真實的呼叫點。他們匯入什麼、呼叫什麼、拿回什麼。[Shape](#shape形狀) 中的型別草稿是從這裡推導出來的，兩者必須一致。當它們分歧時，調整草稿去配合用法，而不是反過來。呼叫者的體驗就是規格，型別是為它服務的。*

## Shape（形狀）

*建議的架構。先寫資料結構，再寫資料如何流經各個簽名。寫出承重的決策。說明哪些不變條件編碼在型別中、驗證放在哪裡，以及系統刻意不做什麼。明確判斷介面深度：說明公開介面隱藏了什麼複雜度、什麼仍然暴露給呼叫者，以及為什麼介面沒有比需要的更大。引用每個決策背後的原則（例如 `per boundary-discipline`），不要重述它。*

## Synthesis decision（綜合決策）

*由 [arena](../../arena/SKILL.md) 填寫。記錄哪個候選成為基底及原因、從其他每個候選改編了什麼，以及拒絕了什麼及原因。*

## Tradeoffs accepted（接受的取捨）

*選定的形狀所做的每個取捨各一個項目。格式：「我們接受 X，以換取 Y。」寫出任何未來的讀者可能誤以為是疏忽的東西，包括看起來像過早最佳化或過早簡化的東西。*

## Alternatives considered（考慮過的替代方案）

*必填。至少寫出一個具體的替代形狀，並用一行說明它為什麼落選。依介面深度評判每個替代方案，而不只是實作的簡單程度。寫出它暴露給呼叫者的複雜度，以及它隱藏的複雜度。當設計空間中有真正的競爭者時，這裡放兩三個替代方案。當限制條件逼出了答案時，一個就夠了，結論寫成「這是唯一可行的形狀，因為……」。避免列出同一個形狀的不同口味。這個章節涵蓋的是選定形狀所考慮並拒絕的設計替代方案，而不是其他執行者的候選。*

## Open questions and risks（未解的問題與風險）

*你在草擬時注意到、需要人類參與判斷的事情，以及在實作開始前值得標出的風險。寫成問句而不是斷言，讓人類的回答就是解決方案，而不只是一則評論。*

## Next implementation step（下一個實作步驟）

*依草稿要建的第一件東西。一句話。綜合後（或如果選擇了檢查點，就是 Phase D 簽核後）你會立刻開始寫的東西。*
