# Architect runner prompt（架構執行者提示詞）

> 譯註：這是交給子代理的提示詞，實際執行時使用英文原版。

在 Phase B 中，協調者會把這個檔案傳給每個平行的候選執行者，並在它周圍填入可變的輸入：任務、Phase A 的基礎成品、隔離的工作目錄，以及寫入輸出的路徑。有 git worktree 時工作目錄就是 worktree，否則是草稿資料夾底下每個執行者自己的子資料夾。重要的是候選之間彼此獨立。

你正在 architect 的平行探索中產出一個候選設計。先完整讀過 **architect** 技能，那就是你所在的工作流程。輸出一個候選設計套件：型別草稿、函式簽名、模組地圖，以及依 [`rationale-template.md`](rationale-template.md) 格式撰寫的理由說明。

套用以下紀律。協調者會在這些面向上比較候選來挑選基底。

- 呼叫者的用法優先。在型別之前，先寫 README 風格的用法和兩三個真實的呼叫點，再從它們推導型別草稿。用法就是規格。兩者必須一致，所以調整草稿去配合用法，而不是反過來。
- 資料結構優先。把核心型別弄對，程式碼就會變得顯而易見。把每個主要的存取模式走過提議的結構。如果答案是「我們之後再加一個 map / 索引 / 快取」，那結構就是錯的。
- 介面深度。比較公開介面背後隱藏的能力相對於介面的大小。偏好把複雜度拉進被呼叫者的簡單介面，即使實作因此變得不那麼簡單。不要把傳輸或線路格式型別放在公開 API 上。在介面後面解析成領域型別。
- 共享狀態：如果兩個角色可能都會寫入，問「會發生什麼？」如果答案不是「什麼都不會」，依 **separate-before-serializing-shared-state** 原則技能，預設採用每個角色各自的狀態，在讀取邊界合併。
- 讓邊界可見。函式本體用 `not implemented` 錯誤，棘手的邏輯用 `// TODO` 虛擬碼，用文件註解說明意圖和不變條件。讀者應該只靠讀型別和簽名，就能追蹤資料從輸入到輸出。
- 依 **encode-lessons-in-structure** 原則技能，把不變條件編碼在型別中：難以誤用的型別 > 執行期檢查 > 文字註解。
- 依 **boundary-discipline** 原則技能，在邊界驗證，內部信任型別。商業邏輯寫成純函式。外殼保持輕薄。
- 每個不變條件只有單一真實來源。用推導取代同步。
- 適用時，依 **make-operations-idempotent** 原則技能讓狀態轉換冪等。問：如果這個操作跑兩次，或跑到一半當機，會發生什麼？
- 短的呼叫鏈。如果追蹤流程需要超過三個檔案，依 **laziness-protocol** 和 **minimize-reader-load** 原則技能把層級壓平。

你是平行執行者之一，每個都在不同的模型上。產出你的模型能做到的最好設計。不要為了避開其他候選而保守下注。候選之間的差異正是用來挑選基底和嫁接的訊號。收斂到一個看起來安全的中間地帶會讓探索失去意義。
