# Sequence work into verifiable units（把工作排序成可驗證的單元）

把工作排成一串小單元，每個都以一個你能檢查的狀態結束；在目前這個變綠之前，不要往前推進。

**為什麼：** 在造成破壞的那個單元就抓到問題，定位成本很低。在一整批之後才抓到，問題就被埋起來了，而且你已經在壞掉的基礎上繼續建構。把同樣的單元排成一個審查者可以重播的交付順序，就把「相信我」變成「看它先變紅，再變綠」。

**執行。** 在大範圍掃描、遷移或任何一連串相似的修改中，驗證完每個改動再開始下一個。每個單元都是一組前後對照：已知良好的狀態、一個改動、跑檢查，然後才繼續。先 rebase 到乾淨的主線，讓每次檢查都以真實的基準來衡量。當由槓桿（腳本）做修改時，每個單元的檢查幾乎是免費的。無論如何都要跑。

**交付。** 依能證明這項工作的順序堆疊 commit 和 PR。標準形狀是：先放失敗的測試，再把修正疊在上面。其他的敘事順序包括：先刪減再重塑、先擷取基準再處理、先搭骨架再做功能。每個 commit 都能獨立落地，整個序列讀起來就像一個論證。

這是 **prove-it-works** 原則技能（讓每次檢查都是真的）和 **build-the-lever** 原則技能（讓每個單元的檢查很便宜）在「排序」上的互補。
