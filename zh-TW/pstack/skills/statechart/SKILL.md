> 譯註：TLA+ 是一種用來描述系統行為並做「模型檢查」的規格語言；TLC 是它的模型檢查器；Mermaid 是一種用文字畫圖的格式。

# Statechart（狀態圖）

這張圖用讀者的語言，呈現系統如何在各個狀態之間移動。讀者就是決定這個行為是否正確的那個人。

## 執行

在 repo 之外的暫存資料夾中工作。寫一份 TLA+ 規格和它的設定檔。然後執行：

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript，所以用能執行 TypeScript 的執行環境來跑它。

第一次執行會用 mise 安裝 TLC 和 Java，需要網路。

## 撰寫規格

- 把讀者同意的每條規則寫成一個 INVARIANT（不變條件）。規則可以是關於某個畫面、某個結果、某個儲存的值或某則訊息。如果模型中沒有對應某條規則的變數，就加上那個變數。永遠不要為了讓規則成立而削弱它。
- 把 `Next` 寫成各個動作的析取（OR），例如 `YouPressPlay \/ YouPressStop`。如果不這樣寫，TLC 會把每一步都叫做 `Next`。
- 沒有任何後續步驟的狀態會違反 `NoDeadlock`（無死結），即使它是一個正確的結束狀態也一樣。當某個 INVARIANT 或 PROPERTY 已經用了那個名稱時，這條規則就叫 `CHECK_DEADLOCK`。在 `Next` 中加一個只在結束狀態成立、什麼都不改變的動作，例如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，並在 `step()` 中給它一個標籤。

## 選擇圖的形式

需要判斷的工作由你來做：每個狀態和箭頭上的文字、階段和它們的顏色、標題，以及給讀者的報告。把你的工作放在一個 view 模組中，並用 `--view` 傳入。

為了呈現讀者的語言，view 匯出 `state(vars)`。`state()` 回傳的值決定形式：

- 字串會產生扁平的圖：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 陣列會產生父狀態：`export const state = (v) => v.main.split(".");`
- 物件會為每個鍵產生一個平行區域：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

用讀者看得到或在意的東西標示每個狀態，例如「付款中」或「已持有租約，寫入待處理」。標籤中不要出現變數名稱。在 `vars` 中，TLA+ 序列是一個鍵從 1 開始的物件，所以 `v.pc[1]` 就是 `pc[1]`。集合是陣列。

view 也可以匯出 `step(action, from, to)`。它會拿到 TLC 的動作名稱，以及該步驟前後的值，並回傳箭頭的標籤。把每個步驟標籤寫成使用者看到它發生的樣子，例如「你按下播放」或「連線失敗」。不要寫出程式碼或 TLA+ 動作的名稱。在圖中結果相同的兩個動作使用相同的標籤，讓它們共用一個箭頭。

當某一步只在某些條件下才能發生時，在它的標籤結尾用方括號加上條件，用讀者的語言，例如 `你按下播放 [在檔案載入期間]`。在區域圖中，指令會在箭頭上用其他區域的標籤文字寫出它們的條件，例如 `[when Offline]`。你的方括號會取代它，這樣從同一個狀態出發的兩個箭頭就可能看起來一樣。所以在區域圖中，不要為其他區域上的條件寫方括號。當一個沒有任何標籤顯示的值決定了某一步會走到哪裡時，在標籤中說出結果，例如「讀取名冊失敗」。

view 還可以匯出這些：

- `group(vars)` 回傳一個階段的名稱。每個圖上的狀態會得到它所屬群組的顏色。當一個圖上狀態背後的模型狀態屬於不同群組時，那個狀態就沒有顏色。
- `colors` 為每個群組名稱指定一個顏色類別。
- `title` 是一個字串，圖會把它顯示在最上方。

指令對每個模型狀態最多呼叫 `state()` 和 `group()` 各一次，對每一步最多呼叫 `step()` 一次。圖和報告都使用那些答案。所以讓每個函式只依賴它的參數。

圖不會畫出停留在同一個標籤內的步驟。當讀者必須看到這樣的步驟時，就把標籤拆開。

目標是大約 20 個箭頭或更少，因為更擁擠的圖很難讀。首先，從 `state()` 回傳更粗略的標籤。給行為相同的值同一個標籤，並省略讀者不需要的細節，例如一個回傳後什麼都不改變的進行中呼叫。保留 bug 路徑上的每個狀態，並保留每個標記。當合併讓一個 `breaks` 狀態變成 `mayBreak` 時，它就隱藏了規則在哪裡被違反。不要合併違反不同規則的兩個狀態，因為那樣讀者就看不出哪條規則在哪裡被違反。如果圖還是太擁擠，對讀者不需要的步驟從 `step()` 回傳 `null`，例如每個狀態都有的重設，或箭頭只是重複其他箭頭已經呈現的步驟。隱藏步驟時遵守這些規則：

- 讓每個圖上的狀態都能從某個起始狀態透過箭頭到達。
- 對每個在模型中有後續步驟的圖上狀態，至少保留一個出去的箭頭。
- 一個箭頭的所有步驟要嘛全部隱藏，要嘛全部不隱藏。只隱藏部分的話，它的條件會變窄。
- 交接時，說明圖隱藏了哪些步驟。

## 讀報告

- 在圖中，違反規則的狀態有 `breaks` 類別。當它背後只有部分模型狀態違反規則時，它有 `mayBreak` 類別。圖例（Legend）會寫出每個標記代表的規則。當兩條規則都被違反時，它會在同一個標記上寫出兩條，所以交接時要說明哪個狀態違反了哪條規則。在區域圖中，當包含某個狀態的每個區域狀態組合都可能違反規則時，那個狀態就會得到標記。當某個組合可能違反規則、而它的狀態都沒有標記時，那個組合中的每個狀態都會得到標記。
- TLC 會越過違反規則的狀態繼續走，所以圖會顯示 bug 之後的狀態。
- 因為 TLC 會越過 bug，一個狀態數沒有限制的模型可能會永遠跑下去。讓常數保持很小，或加上一個 CONSTRAINT。
- 有 VIEW 或 SYMMETRY 時，TLC 會把它視為相同的狀態算成一個狀態，圖也只畫那一個狀態。箭頭可能指向它，而不是指向該步驟實際到達的狀態，報告會說明這一點。
- TLC 會在每個超出 CONSTRAINT 或 ACTION_CONSTRAINT 的狀態中檢查規則，但不會探索那個狀態，也不會檢查它是否死結。當 TLC 對某條規則找到的最短路徑結束在這樣的狀態時，圖會畫出那個狀態，報告會給出那條路徑。圖不會畫出超出上限的其他狀態。這樣的狀態中的死結不會顯示出來。TLC 也會在 ACTION_CONSTRAINT 排除的每一步之後檢查規則，即使它透過其他方式到達了下一個狀態。當 TLC 對某條規則找到的最短路徑以這樣的一步結束時，圖會畫出那一步。
- 指令用一個 worker、以原樣的設定檔用 TLC 檢查規則。當某條規則被違反時，指令會移除那條規則，再跑一次 TLC，直到沒有規則被違反為止。第一次違反之後，每次執行都會在 100,000 個不同狀態時停止，讓大型模型不會永遠跑下去。當某次執行達到那個上限或因錯誤而停止時，報告會在「Rules not checked（未檢查的規則）」下列出它沒有檢查的規則，圖也不會標記它們。沒有被檢查的規則可能成立也可能被違反。要檢查它，就從設定檔中移除被違反的規則，或把模型縮小。這個上限會加入一個改變 TLC 變數順序的模組，所以對於某個性質，TLC 可能會找到和沒有上限時不同的反例。
- `tlc.out` 是 TLC 在原樣設定檔上印出的內容。當圖沒有顯示某條被違反規則的 bug 路徑時，`tlc-RULE.out` 是 TLC 在找到它的那次執行中印出的內容。當 TLC 重複它的第一個警告時，單純執行 TLC 會印兩次，但 `tlc.out` 只顯示一次，因為 TLC 會把第二份從這個指令讀取的輸出中拿掉。這只在 Java 以 `-XX:+UseParallelGC` 執行時發生，因為否則 TLC 的第一個警告就是建議你傳入那個旗標，而它只會印一次。

## 呈現圖

把 `chart.mmd` 以 `mermaid` 程式碼區塊呈現給使用者。圖的預算是 500 個狀態，以 TLC 在原樣設定檔上的計數為準。超過的話，圖只會畫出通往被違反規則的路徑；當沒有規則被違反時，指令不會寫出 `chart.mmd`。它仍然會檢查每條規則，報告也會給出狀態數和每條 bug 路徑。要看完整的圖，就把模型縮小。

用 Pele 渲染圖。當使用者要求圖片，或圖太大、無法以文字閱讀時，依照 `references/render.md`。除非使用者要求，否則不要使用其他渲染器。

## 交接

把每張圖和它的 Mermaid 文字交給必須做決定的人。每個 bug 加一行：規則、讀者對那條規則的描述句，以及報告中編號的路徑。說明模型省略了什麼。給出能重新產生這些檔案的指令，並使用一個新的 `--out` 資料夾。

當模型描述的是程式碼時，對照真實的程式碼重播每條 bug 路徑，可以是測試或實際重現，每個動作一步。如果某個 bug 沒有發生，在你證明模型沒錯之前，先認為是模型錯了。
