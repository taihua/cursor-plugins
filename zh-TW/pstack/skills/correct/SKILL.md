# Correct（糾正）

操作者一直在為同樣的錯誤糾正這個 repo 裡的 agent。改變 repo，讓下一個 agent 犯不了這些錯。

假設每個貢獻者都是一個 agent：它只看得到自己打開的檔案、會複製最近的範例、會走能編譯通過的最短路徑。把 repo 設計成：一個從單一檔案看起來對的改動，對整個 repo 也是對的。

## 找出錯誤類別

首先，讀最近的 commit、還原紀錄、審查留言、agent 指令檔，以及解釋繞路寫法的註解。把錯誤分組成類別。一個類別發生兩次就算數。

## 在最高可行的層級修正每個類別

1. **用架構消除它。** 給每份狀態一個擁有者，給每個任務一種被支援的做法。隱藏內部，讓錯誤的 import 會失敗。用單一真實來源取代手動同步的清單。刪除 agent 可能會複製的舊做法和死程式碼。
2. **用型別強制它，讓壞的狀態寫不出來。** 如果壞的程式碼仍然能編譯，就加一個 lint 或 CI 檢查，讓它的錯誤訊息指出應該改用哪個檔案、型別或函式。如果這個模式已經很常見，就只在改動新增更多時才失敗。
3. **測試行為。** 修正或刪除任何「它檢查的行為壞掉時仍然通過」或「只改內部就失敗」的測試。
4. **文件或 agent 規則最後寫，而且只用於需要判斷的情況。** agent 跳過它們時，什麼都不會失敗。

## 修正並證明

接著，現在就修正最常見的類別，每類一個 commit。證明每個新檢查都會在一個真實的過去錯誤上失敗。在本機和 CI 中跑同一個指令。例外要寫在違規的那一行上，附上理由、到期日和人類的核准。

## 維護規則表

最後，在 agent 指令檔中維護一張表，把每條規則和強制執行它的東西配對。當操作者糾正你時，修正錯誤並加入規則。如果規則早就在那裡、卻沒有任何東西強制執行它，那就是重犯，所以在同一個改動中於最高層級修正它。一旦某個錯誤不可能再發生，就拿掉它的規則。

**回覆：** 每個類別及其證據、你選擇的層級，以及為什麼更高的層級行不通。
