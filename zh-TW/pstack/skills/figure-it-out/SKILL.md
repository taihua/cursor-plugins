# Figure it out（自己想辦法）

當任務沒有符合任何劇本時，就設計一份。在任何程式碼之前，交付物是工作流程本身：一連串的階段，它依任務調整嚴謹程度、執行科學方法，並留下一份人類離開後回來可以稽核的決策紀錄。

## 開始

開一份待辦清單，第一項是讀 **poteto-mode** 技能的「原則」章節。然後把下列各階段加為待辦事項。

## Phase A：界定（Frame）

先打好基礎，再做承諾。在你能說明以下事項之前，不要開始執行：

- 以可被證偽的判定式表達的完成定義（**prove-it-works** 原則技能）。
- 量化的範圍：大致的單元數和工作量，加上打基礎時浮現的阻礙。
- 嚴謹程度，偏向高。單向門（不可逆的決定）和影響範圍大的事情要更嚴謹；可逆、低風險的步驟可以少一點。嚴謹指的是關卡和成品，而不是「更努力」。

在承諾一次長時間執行之前，先呈現界定的內容和取捨。可逆的工作就繼續進行（**never-block-on-the-human** 原則技能），但一次數小時的執行值得一個檢查點。

## Phase B：設計工作流程

拆解成原子性、可以獨立落地的單元。把風險最高的未知數排在最前面。骨架和驗證先於功能（**foundational-thinking** 原則技能）。

- 在工作開始前建好驗證工具，並從改動前的狀態擷取基準，讓檢查讀起來是「舊值 vs 新值」。
- 對於單向門的設計決策，執行 **architect** 技能（它會執行 **arena**）。對於形狀已經很具體的機械式工作就跳過。對已經定案的設計再跑一次 arena 是過度工程（**laziness-protocol** 原則技能）。
- 決定什麼要分派出去。只沿著接縫平行化，並給每個 worker 自己的 worktree 或分支（**separate-before-serializing-shared-state** 原則技能）。不要過度分派。依 **poteto-mode** 技能的「子代理」章節，為每個子代理選擇工作需要的推理等級與快速或標準速度。
- 把設計好的階段清單寫下來。那份清單就是人類要審查的東西。

然後執行這個設計。把它的步驟作為具體項目，加到待辦清單中 Phase C 和 Phase D 之間。每一步都以 Phase C 的迴圈紀律執行，並把 Phase D 的紀錄穿插其中——每落地一步就記一列——而不是把整份紀錄留到最後才寫。

## Phase C：執行迴圈

每個單元都是一次實驗。說明假設、做最小的改動、在真實成品上對照判定式量測，有進展就保留，沒有就還原。套用 **sequence-verifiable-units** 原則技能，驗證完每個單元再開始下一個，而不是把檢查集中到最後。

- 透過檢查成品來驗證，永遠不要依賴自我回報。當某件事太容易通過時，先懷疑觀察方法，再懷疑系統。
- 委派出去的工作要搭配一個評審。如果 worker 鑽了關卡的漏洞，就重設並強化契約。如果關卡本身是錯的，就用它自己的改動修正關卡，而不是繞過它。
- 判定是 VERIFIED（已驗證）、NOT VERIFIED（未通過驗證）或 INCONCLUSIVE（無法判定）。無法判定不算通過。不要隱藏負面結果。

## Phase D：保留稽核紀錄

透過 **show-me-your-work** 技能記錄這次執行。figure-it-out 的工作通常夠有野心，值得把紀錄提交進去，讓審查者能在 PR 中閱讀。紀錄加上 diff，就是讓人類回來後能信任這份工作的東西。

## Phase E：驗證並交回

在真實的產品上（而不只是在測試工具上）對照 Phase A 的判定式檢查整體。把任何反覆出現的糾正編碼成關卡、lint 規則、檢查或腳本（**encode-lessons-in-structure** 原則技能）。

**回覆：** 你設計的劇本、嚴謹程度及原因、決策紀錄的路徑、哪些已對照判定式驗證，以及什麼仍未解決。
