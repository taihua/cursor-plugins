# Interrogate（審問）

對手會試著弄壞一個改動或一個設計。只有當一次實際執行證明了某個發現，它才會留下。回報發現，不要套用修正。

## 界定（Frame）

範圍是使用者指定的東西。否則，就是分支從它與基底分支的合併基準點開始、一直到工作目錄的 diff。依 **in-your-own-words** 技能，從使用者的訊息、commit 和 PR 描述說明意圖。意圖不清楚時問使用者。

## 分派（Fan out）

執行 **arena** 技能 Phase A 的第 3、4 步和 Phase B，但有四個改變：讀取 `interrogate reviewers` 設定行，取代 `arena runners`。把範圍內未提交的修改複製到每個 worktree。每個對手以 `generalPurpose` 派出。取代 arena 的任務與理由說明，給每個對手範圍、意圖和這份任務說明：

> 弄壞這個改動。用一次對真實程式碼的執行證明每個發現，例如一個失敗的測試、一個重現腳本，或顯示錯誤行為的指令輸出。如果是設計或計畫，就跑一個原型或探查目前的程式碼樹。重現用的東西放在你自己的 worktree。每個發現回報一個標題、確切的指令、它印出的輸出，以及意圖所要求的輸出。沒有實際執行過的東西都不要寫。這包括風格、命名、結構，以及需要未來的改動才會成真的風險。沒有發現也是一個有效的結果。

## 驗證（Verify）

依 arena Phase F，重跑每個發現的指令來驗證它。當輸出顯示了失敗、而且那個失敗違反了意圖時，保留這個發現。其餘的放棄。合併根本原因相同的發現。

跳過 arena 的 Phase C、D、E。不同對手會找到不同的失敗，所以判定保留每個經驗證的發現，而不是只採用某一個對手的清單。

## 輸出（Output）

- **Intent（意圖）**：複述的內容。
- **Findings（發現）**：每個經驗證的發現，附上指令、它的輸出、它如何違反意圖，以及找到它的對手。沒有任何發現留下時，寫「no verified findings（沒有經驗證的發現）」。
- **Dropped（被放棄）**：每個對手被放棄的發現數量及原因。
